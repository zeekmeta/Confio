# 使用指南

本文说明 Confio 1.1 的用法。版本变更见[更新日志](../CHANGELOG.md)。

## 安装与编译要求

Confio 及其依赖均从 [NuGet.org](https://www.nuget.org/packages/Confio) 获取，使用默认包源即可，安装不需要 API key：

```sh
dotnet add package Confio --version 1.1.0
```

如果应用的 `NuGet.Config` 禁用了默认包源，需启用 `https://api.nuget.org/v3/index.json`，并使现有包源映射允许 Confio 及其依赖。

项目使用 SDK 风格、`PackageReference` 和 C# 12 或更高版本。当前验收工具链为 .NET 10 SDK，编译工具版本与运行时独立。需要验证源码对应的包时，使用[本地候选包](./开发与验证.md#本地候选包)。

## 支持范围

生成器随 NuGet 包交付。应用声明模型和一个原生 JSON 上下文，Confio 自动生成配置节、默认构造、保护和类型服务声明。需要业务约束的模型实现 `IValidatableSettings`，直接使用和 DI 共用同一规则。

| 应用目标 | NuGet 自动选择 | 发布方式 |
| --- | --- | --- |
| .NET Framework 4.6.2 / 4.7 / 4.7.1 / 4.7.2 / 4.8 / 4.8.1 | 分别为 `net462` / `net47` / `net471` / `net472` / `net48` / `net481` | Windows 托管应用 |
| .NET 8 / 9 | `net8.0` | JIT、Native AOT |
| .NET 10 | `net10.0` | JIT、Native AOT |

NuGet 包包含八个运行库资产及对应依赖组。Framework 各目标分别编译、还原依赖和验证，NuGet 自动选择对应资产；这些资产仍由同一个工程和同一个包交付，共享模型、API 与文件行为。分目标编译不等于已在各版本原始运行时实测，具体证据见设计第 8.1 节。

低版本通过包依赖自动取得所需 JSON 静态元数据 API；Framework 的 AES-GCM 由微软官方兼容库提供，PolySharp 提供编译期语言辅助，使用 `record/init` 不必手写辅助类型。各目标共用以下模型和 API，不需要额外选择“兼容模式”或“AOT 包”。Framework 消费项目需显式设置 `<LangVersion>12.0</LangVersion>`；`DateOnly` 等仅在现代 .NET 存在的 BCL 类型不由 Confio 补造。

不支持 .NET 5 / 6 / 7。各正式目标统一使用 JSON 10 和 Microsoft.Extensions 10 所提供的能力，不保留旧依赖或专用兼容分支。

## 声明模型

```csharp
using Confio;
using System.ComponentModel.DataAnnotations;
using System.Text.Json.Serialization;

[SettingsSection("Mail")]
public sealed class MailSettings : IValidatableSettings
{
    public string Host { get; set; } = "localhost";
    public int Port { get; set; } = 587;

    [Protected]
    public string Password { get; set; } = "";

    public void Validate()
    {
        if (string.IsNullOrWhiteSpace(Host))
            throw new ValidationException("The mail host is required.");
        if (Port is < 1 or > 65535)
            throw new ValidationException("The mail port must be between 1 and 65535.");
    }
}

[SettingsSection("Retry")]
public sealed record RetrySettings : IValidatableSettings
{
    public int MaxAttempts { get; init; } = 3;

    public void Validate()
    {
        if (MaxAttempts < 1)
            throw new ValidationException("At least one retry attempt is required.");
    }
}

[JsonSerializable(typeof(MailSettings))]
[JsonSerializable(typeof(RetrySettings))]
public partial class AppSettingsContext : JsonSerializerContext
{
}
```

## 读取、保存与更新

以下代码放在方法体中：

```csharp
using var config = new ConfigurationFile(
    AppSettingsContext.Default);

var mail = config.Read<MailSettings>();
mail.Host = "smtp.example.com";
mail.Port = 465;
config.Save(mail);
```

同一实例提供 `ReadAsync`、`SaveAsync`、`UpdateAsync`、`ResetAsync`、`ReloadAsync`，均返回 `Task` 并接受取消令牌。同步与异步消费都使用普通 `using`，首次读写自动加载，不需要先初始化。读取返回独立副本；修改副本后显式保存，或用 `Update` / `UpdateAsync` 基于最新文件修改。

需要自定义位置时传入 `path: "settings.json"`，相对路径在创建时按当前工作目录解析并固定。没有 `ApplicationId` 参数。模型标记为 `[SettingsSection]` 时直接读写文件根对象，`[SettingsSection("Mail")]` 则拥有 `Mail` 节；同一文件的根模型不能再与子节模型重叠注册。

| 要做的事 | 使用入口 | 实际效果 |
| --- | --- | --- |
| 读取当前生效配置 | `Read<T>()` | 首次加载并自动保护文件中的明文，之后从最近成功的内存配置返回副本；不会每次读取磁盘 |
| 保存一份完整编辑结果 | `Save(model)` | 完整替换目标模型节；旧草稿也会覆盖该节的新值 |
| 在最新配置上修改 | `Update<T>(edit)` | 在文件锁内读取磁盘最新值，执行一次修改并保存；应用不管理文件锁或重试 |
| 恢复某个模型的默认值 | `Reset<T>()` | 删除该节的持久化覆盖，采用模型默认值；例如默认端口是 `587`，恢复后就是 `587` |
| 采用外部文件修改 | `Reload()` | 重新读取并自动保护声明位置的明文，成功后更新生效配置；失败保留之前成功的内存配置 |

保存、更新或重置保留其他配置节的数据与已有密文，并将其他所选声明位置的待保护明文合并到同一次提交；完整替换目标节时，该节内未被模型承载的未知属性不保证保留。JSON 输出保留中文等常用 Unicode 文本的可读性，引号、控制字符和换行仍按 JSON 规则转义；不承诺原注释、排版或 YAML 锚点写法保持不变。

`Update` 同时接受修改副本的 `Action<T>` 和返回新模型的 `Func<T,T>`。`record/init` 模型使用 `with`，文件协调和保存由组件完成：

```csharp
await config.UpdateAsync<RetrySettings>(retry =>
    retry with { MaxAttempts = checked(retry.MaxAttempts + 1) });
```

业务校验在首次加载、重载和提交前执行，失败抛出 `ValidationException`，保留文件与最近的有效快照，不发出变化通知。已加载的普通读取不重复校验；`Reset` 也要求模型默认值有效。校验只读取模型，不做 I/O；消息描述规则，避免包含敏感值。它与原生 Options 的创建后校验有不同的执行时点，详见[业务校验契约](./设计方案.md#46-模型业务校验)。

## 变化通知与错误处理

直接使用 `config.OnChange<T>(listener)`，或在容器中调用 `ISettings<T>.OnChange(listener)`，即可订阅共享文件的变化：

```csharp
using var subscription = config.OnChange<MailSettings>(mail =>
    System.Console.WriteLine($"当前端口：{mail.Port}"));
```

订阅不加载文件、不立即回调。成功保存、重置和重载后，每个订阅者获得当前模型的独立副本；同文件其他节的提交也会通知。回调在锁外执行，不保证 UI 线程；释放返回值可退订，回调异常通过诊断报告，不回滚保存。Avalonia 示例已演示 UI 调度和退订。

`OnChange` 不会自动监听外部文件，外部编辑后仍需调用 `Reload`。格式损坏、业务校验失败、解密失败都会报告，不能统一重置为默认值；修正配置或密钥后可重新加载。备份、恢复与历史管理不属于当前产品范围。Sample 的恢复按钮只还原它自己制造损坏前保留的演示原文，具体见[错误处理与功能边界](./设计方案.md#47-错误处理与功能边界)。

## 文件格式

默认通过 `path` 的扩展名选择格式，`.yaml` 与 `.yml` 等价；也可用 `ConfigurationFileOptions.Format` 显式指定，支持 `.conf` 或无扩展名文件。JSON、YAML、TOML、INI 使用相同的模型、上下文和读写 API：

```csharp
using var config = new ConfigurationFile(
    AppSettingsContext.Default, path: "settings.conf",
    options: new ConfigurationFileOptions { Format = ConfigurationFormat.Toml });

var mail = await config.ReadAsync<MailSettings>();
mail.Port = 465;
await config.SaveAsync(mail);
```

| 扩展名 | 可用范围与主要限制 |
| --- | --- |
| `.json` | 对象、数组、标量、`null`，允许注释与尾逗号输入 |
| `.yaml` / `.yml` | YAML 1.2 Core 的字符串键映射、数组、标量、`null` 与已完成锚点的别名；字符串 `00123` 需要加引号 |
| `.toml` | 表、数组、标量和原生日期；支持空容器、多行字符串，没有原生 `null`；原生整数为有符号 64 位，浮点为有限 binary64，保存不能往返的高精度数值会报错 |
| `.ini` | 原生 INI 行与节规则，用 `:` 表示层级，数组用从 `0` 开始的连续索引；本项目的固定方言不支持 `null`、空容器和多行值 |

INI 根据静态模型判断类型：`Port=465` 进入整数属性，`Code=00123` 进入字符串属性并保留前导零。常见数值、布尔、枚举和日期类型由组件处理；不能确定明文形态的自定义转换器在创建文件实例时拒绝，整体保护后的载荷不受这一限制。

JSON、YAML、TOML 的文件键及字典键区分大小写，模型属性匹配遵守 JSON 上下文的 `PropertyNameCaseInsensitive`；INI 使用本方言不区分大小写的键规则。原生 Configuration 的扁平键冲突只在接入该视图时检查。默认完整保存模型；显式属性级 `JsonIgnore` 条件遵守原生序列化语义，省略的属性再次读取时会采用默认值。

格式限制针对实际写入数据检查，不会悄悄省略属性或改为空字符串。例如整体保护的非空子对象先变成一条密文，其内部可以含 `null` 或空集合；属性本身是 `null` 时，TOML / INI 仍无法保存。保存保留其他配置节的数据语义与密文，包括 TOML 原生日期与普通字符串的区别；注释与原排版不承诺保留。完整边界见[格式约定](./设计方案.md#52-格式表达边界)。

模型可以声明可空属性，由实际保存的值决定是否超出格式范围。格式适配发现无法表达的值时抛出 `ConfigurationValueException`，提供 `Format`、`Path` 和 `Reason`；文件、旧快照与通知保持不变，应用不需要先做一轮格式检查。开发者可以直接看到具体位置与原因，例如：

```text
TOML cannot persist null at '/Mail/Password'.
INI cannot persist an empty collection at '/Mail/Recipients'.
```

`Path` 使用 JSON Pointer，例如 `/Mail/Recipients/0` 指向第一个元素，路径段中的 `~`、`/` 分别写为 `~0`、`~1`。界面可根据结构化属性生成自己的提示，无需解析异常正文或显示配置值。

容器入口也通过同一个 `path` 参数选择格式。四种格式共用静态 JSON 模型元数据；TOML 使用库内固定节点上下文，应用无需额外声明 TOML 上下文。所有目标统一接受 TOML 1.1，包括 `\e`、`\xHH` 转义、多行和末尾逗号内联表及省略秒的时间。读取校验重复键等非法语法，失败保留原文件与上一次成功的配置，JIT 与 Native AOT 使用同一路径。

## 文件编码

默认读写 UTF-8，保存不带 BOM。通过 `ConfigurationFileOptions.Encoding` 指定其他编码，直接创建、普通 DI 与原生接入共用此选项：

```csharp
using System.Text;

using var config = new ConfigurationFile(
    AppSettingsContext.Default, path: "settings.ini",
    options: new ConfigurationFileOptions
    {
        Encoding = CodePagesEncodingProvider.Instance.GetEncoding("gbk")!
    });
```

代码页支持随所需框架资产交付，应用无需注册全局 Provider 或预先转码。`Encoding.Unicode` 表示 UTF-16 LE、有 BOM；`new UTF8Encoding(true)` 表示 UTF-8、有 BOM。创建或注册时复制并固定编码，后续修改选项不影响已有文件实例。

读取时 UTF-8、UTF-16、UTF-32 的 BOM 优先于选项；无 BOM 时使用选项，不猜测旧代码页。保存始终使用所选编码及其 BOM 设置，包括加载明文后自动加密的写回。例如，默认设置读取 UTF-16 BOM 的 JSON 后，下一次写回会成为 UTF-8 无 BOM；需要保持 UTF-16 时显式选择 `Encoding.Unicode`。

可以显式使用 `Encoding.Default`，但它不是文件编码检测：Framework 中为系统活动代码页，现代 .NET 中为 UTF-8。跨机器使用 GBK 文件时应明确选择 GBK，而不是依赖系统设置。

| 格式 | 文件编码 |
| --- | --- |
| JSON | 默认 UTF-8，本地封闭用途可显式选择其他编码；对外交换使用 UTF-8 |
| YAML / YML | UTF-8、UTF-16、UTF-32 |
| TOML | UTF-8 |
| INI | 所选 `Encoding` 支持的编码，包括 GBK |

不符合格式要求的编码在创建时抛出 `NotSupportedException`，输入 BOM 指示不支持的编码时在读取时报告。组件在编码副本中启用异常回退：非法字节或无法表示的输出字符抛出 `InvalidDataException`，不沿用有损字符替换，也不修改传入的编码对象。失败保留原配置文件及已有成功快照，错误不包含配置原文。

编码只影响配置文件文本，受保护值内部仍使用 UTF-8 JSON，二进制密钥文件也不受影响。GBK 文件中的受保护字符串可以包含 emoji，因为持久化的是密文；未保护的 emoji 文本若无法编码则保存失败。

## DI、Configuration 与 Host

普通容器每个文件注册一次，应用服务直接注入 `ISettings<MailSettings>`，使用同样的类型读写方法：

```csharp
services.AddConfigurationFile(
    AppSettingsContext.Default, path: "appsettings.json");
```

文件和类型服务默认是单例，文件由根容器释放；需要复用外部实例时使用 `services.AddConfigurationFile(config)`，仍由调用方释放。注册和解析服务不加载文件。完整示例见[容器接入示例](../samples/ConfioSample/IntegrationExamples.cs)，详细语义见[读写与容器契约](./设计方案.md#4-读写-api提交与原生读取视图)。

不同模型可以分别注册到不同文件，每个 `ISettings<T>` 自动绑定其所属文件。同一类型不能在容器中重复归属；需要同模型的多个文件时直接使用文件实例。单文件应用可以直接注入 `ConfigurationFile`；多文件时通过类型服务读写，或用 `IEnumerable<ConfigurationFile>` 获取已注册文件。

需要原生 `IConfiguration` 和 Options 时，注册入口先完成预加载，再调用原生 `BuildServiceProvider()`。以下代码位于异步方法中，不再对同一模型调用普通注册：

```csharp
using var configuration = new ConfigurationManager();
await services.AddConfigurationFileAsync(configuration, AppSettingsContext.Default);
using var provider = services.BuildServiceProvider();

var mail = provider.GetRequiredService<IOptionsMonitor<MailSettings>>().CurrentValue;
```

Host 使用原生构建器；需要只加载选定文件时，从空构建器开始。日志输出和业务服务按应用需要选择：

```csharp
var builder = Host.CreateEmptyApplicationBuilder(null);
await builder.AddConfigurationFileAsync(AppSettingsContext.Default);
builder.Logging.AddConfiguration(builder.Configuration.GetSection("Logging")).AddConsole();
builder.Services.AddHostedService<MailWorker>();
using var host = builder.Build();

await host.RunAsync(cancellationToken);
```

上述原生类型来自 Microsoft.Extensions 的对应命名空间；使用 Host 的应用自行引用 `Microsoft.Extensions.Hosting`，Confio 仅依赖 Host 抽象。两个 `Add` 入口均有同步版本、上下文集合和已有文件重载。应用无需逐模型绑定或编写 Options 工厂。预加载失败由组件清理自建文件；接入成功后，自建文件随 ConfigurationManager 或 Host 释放。Confio 不接管其他服务的构建失败，普通配置根由上例的 `using` 管理。

`IConfiguration` 保留原生配置源优先级。Confio 的默认命名 Options 从文件快照创建，再执行原生 `Configure/PostConfigure/Validate`；其他 Provider 的值不会自动进入该文件或这些 Options。保存、更新、重置和显式重载会刷新 `IOptionsMonitor<T>`，`IOptions<T>` 和已有作用域的快照保留原生缓存。编辑使用文件或 `ISettings<T>` 的副本；Provider 只读。外部文件修改可通过 `IConfigurationRoot.Reload()` 或 `ConfigurationFile.Reload/ReloadAsync` 获取，均复用同一文件加载与保护路径；首次构建复用预加载结果。原生根沿用自己的通知行为，不保证单次 Reload 只发出一次根通知。完整启动与所有权规则见[原生读取接入](./设计方案.md#75-原生读取接入与启动)。

## 文件与密钥路径

省略 `path` 时使用当前用户的应用配置目录，`<app>` 取入口程序集简单名称，不含版本号。实际路径通过 `config.Path` 查看；自动密钥位置通过 `config.KeyFilePath` 查看。两种路径都可单独指定：

| 平台 | 默认配置文件 | 默认自动 AES 密钥文件 |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%/Confio/<app>/appsettings.json` | `%LOCALAPPDATA%/Confio/keys/<app>.key` |
| macOS | `~/Library/Application Support/Confio/<app>/appsettings.json` | `~/Library/Application Support/Confio/keys/<app>.key` |
| Linux | `$XDG_CONFIG_HOME/Confio/<app>/appsettings.json` | `$XDG_DATA_HOME/Confio/keys/<app>.key` |

Linux 未设置上述变量时分别使用 `~/.config` 和 `~/.local/share`。显式格式会改变默认文件的扩展名。自定义配置路径不自动改变密钥位置；有部署要求时同时指定 `KeyFilePath`。未使用自动 AES 时，`config.KeyFilePath` 为 `null`。

## 字段保护

不存在的文件读取默认值，不落盘。`[Protected]` 可以保护有静态元数据的字符串、值类型或整个子对象；保存自动加密，加载普通明文时默认自动保护写回，空字符串和 `null` 不调用密钥设施。

文件密文统一使用 `enc:v1:<Base64>` 字符串。文件输入中受保护位置的 `enc:` 是保留前缀，带该前缀的手写明文会按密文解析；版本、编码或认证失败会报错。通过模型 API 保存时，值始终按明文处理，即使密码本身以 `enc:v1:` 开头也能完整往返。读取已有密文不会重复加密写盘，未声明保护的普通字段不按前缀解密。

例如，手写一份普通明文配置：

```json
{"Mail":{"Password":"smtp-password"}}
```

首次 `Read` 或显式 `Reload` 校验通过后，组件将 `Password` 自动替换为 `enc:v1:<Base64>` 密文，应用仍读到 `smtp-password`，无需额外调用保存。缺失的默认属性不会补写。需要只读加载手写明文时，设置 `ProtectPlaintextOnLoad = false`；后续显式保存、更新和重置仍按保护规则提交。四种格式使用相同规则。

默认 `Protection = ConfigurationProtection.Auto`：Windows 使用当前用户 DPAPI；macOS / Linux 使用自动文件密钥的 AES-256-GCM，无需 Keychain、Secret Service 或桌面授权。Windows 也可以显式选择 AES：

```csharp
using var config = new ConfigurationFile(AppSettingsContext.Default,
    options: new ConfigurationFileOptions
    {
        Protection = ConfigurationProtection.AesGcm
    });
```

自动密钥只在第一次需要加密且没有密钥文件时随机生成，保存成功后才提交密文；后续进程复用同一文件。Windows 自动 AES 的密钥文件由当前用户 DPAPI 包裹；macOS / Linux 新建密钥文件权限为 `0600`，新建私有目录为 `0700`。已有目录权限不擅自修改。这依赖用户账户与文件权限，不等同于系统钥匙串的访问控制。

服务器、Docker 或跨机器共享配置时，在同一个入口传入部署环境提供的稳定 32 字节随机密钥，即使用内置 AES-256-GCM；Windows、Linux、macOS 使用同一实现。应用无需创建保护器或管理算法参数：

```csharp
using var config = new ConfigurationFile(
    AppSettingsContext.Default,
    options: new ConfigurationFileOptions { EncryptionKey = key });

// 普通 DI、原生 Configuration / Options 和 Host 接入使用同一个选项类型。
services.AddConfigurationFile(
    AppSettingsContext.Default,
    options: new ConfigurationFileOptions { EncryptionKey = key });
```

显式 `key` 由应用的部署或凭据设施提供，保持稳定，组件复制使用，不额外保存。也可仅指定 `KeyFilePath`，让组件在该位置自动生成和复用密钥；这两种来源均使 `Auto` 选择 AES，不能同时指定。选择 DPAPI 不接受 AES 密钥选项；高级设施通过 `ConfigurationFileOptions.Protector` 接入，始终借用，不与内置选择混用。

缺少已有密文的密钥、密钥损坏或认证失败时明确报错，保留配置，不创建替代密钥。跨应用或机器使用同一密文需要相同 AES 密钥和逻辑字段路径，解密不依赖程序集名或配置文件位置。Windows DPAPI 及 Windows 自动 AES 密钥文件仍绑定当前用户环境；可移植部署应显式管理共享密钥。具体契约见[密钥规则](./设计方案.md#62-密钥默认与替换)。
