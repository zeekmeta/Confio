# Confio 设计方案

状态：1.1.0 已正式发布，公开 API 与持久化配置格式按 1.0 基线维护兼容。已实现能力与平台证据见第 8.1 节，发布记录见更新日志，后续实施顺序见第 8.2 节。

本文统一维护 Confio 的目标、取舍、消费方式和待验证事项。项目入口见 [AGENTS.md](../AGENTS.md)，工程及验收规则见 [开发规范](../开发规范.md)。

## 1. 目标与非目标

目标是一个独立的 .NET 配置组件：一个应用选择一个配置文件，多个配置模型共享该文件；格式、加密和源生成不改变应用的读写方式。无 DI 程序、普通容器和 Host 使用同一配置运行库。

### 1.1 已明确的需求

- 通过一个 NuGet 包提供配置读写能力，支持直接创建对象、普通 DI 和 Host 接入。
- 读取、保存、更新、重置和重载均提供同步与异步入口，应用无需单独初始化文件实例。
- 默认一个文件同时负责读取与保存，模型提供默认值，不另建默认值配置文件。
- 首批完整覆盖 JSON、YAML/YML、TOML、INI 的约定配置语义，不能只完成 JSON 就宣称组件完成。
- 支持指定字段及子对象的持久化保护，读取时解密；允许应用持久化需要恢复原文的密码和其他敏感配置。
- Native AOT 是正式主路径，验收包含真实读写、加解密和目标平台运行。
- 源生成器是首版正式能力，减少注册和保护声明，不要求应用按文件格式重复定义模型。
- 与原生 `IConfiguration`、Options 和 `ILogger<T>` 协作，不建立替代它们的通用基础设施。
- Confio 提供默认文件与目录约定、通用注册和文件生命周期接线，应用只表达业务差异。

1.0 建立首个正式的公开 API 与持久化格式兼容基线，不保留此前内部预览版的兼容入口。同一主版本维护已公开契约，破坏性调整通过大版本处理；版本规则见开发规范第 5.4 节。实现和验收使用隔离目录，失败时保留源文件。

### 1.2 明确不做

不建立多文件环境叠加、配置中心、云同步、运行时插件扫描、通用事务与编辑冲突合并、自动设置 UI、自研对象序列化器、旧格式迁移或密钥管理平台。文件备份、恢复与历史管理不属于当前产品范围，也不作为配置核心完成的条件。默认不增加文件监听、自动重试业务更新、后台保存队列或退出时集中保存。

组件负责配置数据及其持久化保护，配置的业务用途和生效方式由应用决定。配置文件不作为数据库、业务审计或大型状态存储。

## 2. 责任边界与交付

### 2.1 配置组件

项目、NuGet ID 与根 namespace 统一使用 `Confio`。本仓库维护源码、依赖、版本、文档与发布。

公开安装入口为 [NuGet.org](https://www.nuget.org/packages/Confio)，用法维护在[中文 README](../README.zh-CN.md#安装)，完整发布步骤维护在[开发与验证](./开发与验证.md#发布)。包版本统一由 `Directory.Build.props` 管理，上传经过验收的同一份包，已发布版本不覆盖。

正式源码为 `Confio` 与 `ConfioGenerator` 两个项目、一个 NuGet 包，运行库与编译期生成器随同交付，JIT 与 AOT 共用同一资产。目录与工程规则见[开发规范第 2 节](../开发规范.md#2-工程与-api)，测试和示例不另算发布组件。

| 项目 | 目标 | 职责 |
| --- | --- | --- |
| `Confio` | `net462;net47;net471;net472;net48;net481;net8.0;net10.0` | 同一配置运行库；Framework 在 Windows 消费，.NET 8 / 9 / 10 服务 JIT 与 Native AOT |
| `ConfioGenerator` | `netstandard2.0` | 编译期增量源生成，随运行库包作为分析器交付，不进入应用运行时 |

.NET 10 LTS 是主要开发目标，同时提供 .NET 8 / 9 及 Framework 4.6.2 起的消费能力。消费版本与打包资产分开维护，具体平台证据见第 8.1 节：

| 消费范围 | 资产与验收要求 |
| --- | --- |
| .NET Framework 4.6.2 / 4.7 / 4.7.1 / 4.7.2 / 4.8 / 4.8.1 | 分别选择 `net462` / `net47` / `net471` / `net472` / `net48` / `net481` 资产；Windows 同步、异步及静态模型消费，不支持 Native AOT |
| .NET 8 / 9 | 选择 `net8.0` 资产；JIT 与 Native AOT 使用相同实现 |
| .NET 10 | 选择 `net10.0` 资产；JIT 与 Native AOT 使用相同实现 |
| 模型类库 | 与运行库采用相同的八个目标声明模型及上下文，验证跨项目消费 |
| .NET Framework 4.6 / 4.6.1、.NET 5 / 6 / 7 | 不纳入支持矩阵；不保留对应资产、旧依赖或专用兼容分支 |
| .NET Standard 运行库 | 不单独交付；生成器目标与第三方包的 Standard 资产不扩展 Confio 的应用目标范围 |

当前源码通过一个 NuGet 包在 `lib/<TFM>/` 提供上表八个运行库资产及对应依赖组。Framework 各版本分别编译、还原依赖和验证，共享同一工程、源码和 API；分资产不引入独立实现或版本序列。.NET 9 复用 `net8.0`，真实消费者逐个验证。生成器仍以 `netstandard2.0` 构建并放在分析器目录，该目标只服务编译器加载。NuGet 按消费项目目标选择资产，不依据机器安装的运行时或应用是否启用 AOT 决定；分目标编译与可解析范围不等于已在相应原始运行时实测。

Native AOT 是现代应用的发布方式。同一现代目标的托管程序集可供 JIT 使用，也可作为 Native AOT 编译输入；应用发布后生成相应平台的本机程序。Confio 不因此拆出 AOT 包，也不按发布方式维护两套配置行为。

配置文件、快照、校验、保护封装、模型转换与接入 API 共用实现。Framework 只编译 Windows 系统保护入口，AES-GCM 使用微软兼容包，语言辅助类型使用 PolySharp；所有目标的密文协议相同。自动 AES 密钥共用同一文件流程，仅在 Windows 密钥包裹及 Unix 文件权限的实际 API 差异处处理。`DateOnly`、`TimeOnly`、`Half`、`Int128` 等类型仅在提供它们的运行时适用，不由 Confio 仿造 BCL 类型。

完整交付要求上述运行时提供相同配置能力，包括同步与异步操作、四种格式、默认值、字段保护和源生成接入。现代目标两种发布方式共享静态模型元数据和配置语义；Framework 同样通过静态上下文消费。格式的值表达限制保持一致，不因运行时适配引入 null 编码、数据清洗或不同默认值。

生成器输出随消费项目编译。仓库与真实消费者统一使用 .NET 10 SDK、C# 12，应用可以选择 SDK 支持的更高语言版本，Confio 不覆盖应用的 `LangVersion`。Framework 消费采用 SDK 风格项目及 `PackageReference`，同样设置 C# 12；编译工具版本与应用运行时独立。PolySharp 作为 Framework 依赖传递编译期辅助类型，支持 `record/init` 等语法，应用不手写 `IsExternalInit`。Framework 4.6.2 / 4.7 的 Standard 依赖兼容程序集及绑定重定向由 SDK 自动处理，不要求应用复制 DLL、手写重定向或引入 Confio 专用兼容层。Confio 生成器以 Roslyn 4.8 API 构建，测试与原生 JSON 生成器共同生成、编译并运行；正式消费验收以 .NET 10 工具链为准，不另承诺旧 SDK、旧式 `packages.config` 或 C# 9 消费基线。

已实测工具链包括 Windows 的 SDK 10.0.401（仓库构建）和 Ubuntu 24.04 的 SDK 10.0.112（隔离包消费与 Native AOT）。`net10.0` 的 JSON 库和原生生成器使用 SDK 资产；Framework 各目标和 `net8.0` 引用 System.Text.Json 10.0 系列。模型结构、集合元素及构造参数关联直接使用原生静态元数据，Confio 生成器仅提供配置声明、保护和默认构造接线。

外部依赖版本统一维护在 [Directory.Packages.props](../Directory.Packages.props)，不设置 `SuppressTfmSupportBuildWarnings` 绕过依赖下限。.NET 8 / 9 的官方支持截至 2026-11-10，.NET 10 LTS 截至 2028-11-14。后续维护范围随实际需求和官方周期评估，不机械增加目标。

依据：[.NET 支持策略](https://dotnet.microsoft.com/en-us/platform/support/policy/dotnet-core)、[目标框架](https://learn.microsoft.com/en-us/dotnet/standard/frameworks)、[Native AOT 目标要求](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/#target-framework-requirements)。这些机制支持上述设计，不替代格式库、加密设施及整包消费实测。

配置运行时负责文件加载、模型默认值、配置节声明、读写与重置、字段保护、提交快照以及原生配置读取投影。

内部只有一个文件状态与提交责任方。格式适配负责解析、输出和必要的节点适配，不分别绑定业务模型；保护实现只负责敏感节点的保护与恢复；各类型服务不另建文件、缓存、文件锁或监听器。

初期采用一个配置运行时 NuGet 包，交付已要求的格式能力；生成器作为独立编译工程随包作为分析器提供，应用运行时不引用 Roslyn。没有已验证的依赖隔离收益前，不按格式、读取、写入、加密和声明拆出一组包。版本和依赖由本仓库统一管理。

格式差异形成实际的内部适配边界，但不因此公开插件注册框架。不同部署环境的保护设施有真实差异，可以提供一个明确的保护实现替换入口；不要求普通应用了解它。

### 2.2 通用集成

原生 DI、Configuration、Options 和 Host 接入由 Confio 提供。应用按所需读取入口选择消费方式：

| 消费需要 | 入口 | 首次加载时机 |
| --- | --- | --- |
| 直接创建对象并读写 | `new ConfigurationFile(...)`，见第 7.3 节 | 首次明确读写操作 |
| 在业务服务中注入文件或 `ISettings<T>` | 一次 `services.AddConfigurationFile(...)`，见第 7.4 节 | 首次明确读写操作 |
| 通过 Configuration / Options 供原生消费者读取 | 组件的原生启动接入，见第 7.5 节 | 最终容器或 Host 构建前预加载 |

使用 Host 的应用如果只需要类型读写，同样采用普通注册。所有消费方式共享文件运行时；普通注册返回原生 `IServiceCollection`，具体契约见第 4.5 节。组件承担逐模型接线、加载和生命周期管理，应用不复制 Options 工厂或失败清理流程。

目录、文件格式和保护选择在加载前确定，随后复用同一结果进入 DI。不能先打开文件，再通过后置注册替换目录，形成两份路径事实。Confio 不替代日志设施；日志等原生消费者可读取同一 Configuration / Options 视图。

### 2.3 应用

应用声明业务配置模型、默认值、业务校验、需要保护的成员和类型上下文，决定业务修改及保存时点。配置保存与业务生效分开：组件提交数据，具体能力决定是否立即应用、重建资源或下次启动生效。

## 3. 文件、默认值与配置节

### 3.1 一个选定文件

一个 `ConfigurationFile` 管理一个选定文件。默认文件名为 `appsettings.json`；显式 `path` 优先，相对路径在创建或注册时按当前工作目录解析并固定。构造不创建目录，实际写入时才创建必要目录，权限失败不转移到另一处保存。

省略路径时，组件使用当前用户的应用目录；`<app>` 是入口程序集简单名称，不含版本号，不参与加密认证。Windows 使用 `%LOCALAPPDATA%/Confio/<app>/`，macOS 使用 `~/Library/Application Support/Confio/<app>/`，Linux 使用 `$XDG_CONFIG_HOME/Confio/<app>/`，未配置 XDG 时使用 `~/.config/Confio/<app>/`。无法取得应用名时，可显式提供配置路径及实际需要的密钥来源。没有公开的 `ApplicationId` 参数。

默认按扩展名识别 JSON、YAML/YML、TOML、INI；`ConfigurationFileOptions.Format` 的显式选择优先于扩展名，支持 `.conf` 或无扩展名文件。未指定路径时，显式格式决定默认文件名的扩展名。缺少显式格式且扩展名未知时明确失败，不轮询解析器猜测格式，也不寻找其他配置文件。

读取与保存始终指向同一文件，不按模型另建文件，不叠加环境专属配置。文件路径与格式在加载前确定，不能从尚未读取的文件自身取得。安装目录不作为默认写入位置；临时提交文件、协作锁及独立密钥文件各有明确职责。

Host 的其他配置来源由原生构建器选择。仅需本文件时使用 `Host.CreateEmptyApplicationBuilder`；接入已有 Host 时保留已有来源及优先级，不通过清除 Provider 撤销已经发生的读取。

### 3.2 默认值

默认值只有一个声明位置：模型属性初始化或可无参调用的构造函数。生成器输出静态构造调用，不复制属性初始值或另建默认值常量，应用也不重复填写默认值配置表。

| 输入或操作 | 语义 |
| --- | --- |
| 文件不存在 | 使用默认值，不因读取而创建文件或目录 |
| 缺少配置节或属性 | 采用模型构造和约定反序列化规则提供的默认值 |
| 显式值 | 使用已保存值，不因它恰好等于默认值而自动删除 |
| 显式 `null` | 与缺失不同；模型和格式需要能够表达 |
| 首次保存 | 写入目标配置节的完整值，不强制生成所有配置节 |
| 恢复默认 | 删除该配置节的持久化覆盖，再采用当前模型默认值；文件或覆盖不存在时不新建配置文件 |
| 文件损坏或值不能转换 | 明确失败，不静默退回默认值或覆盖源文件 |

默认值在建立读取快照时应用。`Read`、`ReadAsync` 每次取得独立副本；Confio 的 Options 工厂在创建 Options 时取得副本，后续取值遵守第 4.4 节的原生缓存语义。两者不各自重新解释缺失值，模型转换遵守第 5.1 节的固定规则，不自建通用深度合并算法。

缺失的嵌套属性保留构造后的值；文件显式提供嵌套对象时，按原生 JSON 的替换语义创建该对象并应用其自身默认值，不深度叠加父对象对旧实例的赋值。数组和集合完整替换，不追加初始项或保留旧尾项。例如未声明范围校验的模型中 `Port` 默认是 `587`，显式保存 `0` 后仍须读到 `0`；只有重置或文件中缺失该属性才重新采用默认值。

`record/init` 使用相同规则。System.Text.Json 10 系列的原生生成器将 `init` 成员作为构造参数，缺失时可能以 CLR 零值覆盖属性初始化值；Confio 在现有节点规范化中，用生成的静态默认构造补齐这些缺失成员，然后交给同一份 JSON 元数据转换。该处理覆盖嵌套对象与集合元素，保留显式 `null`、零值和空容器，不把它们替换成默认值；构造函数参数自身的默认值仍由原生元数据处理。

### 3.3 配置节归属

`[SettingsSection("Mail")]` 声明模型拥有 `Mail` 节，冒号分隔嵌套路径；`[SettingsSection]` 声明模型直接拥有文件根对象，不从 CLR 类型名推导节名。JSON、YAML、TOML 的节名区分大小写，INI 沿用所选方言不区分大小写的规则。

同一文件的模型归属须唯一：同一模型重复声明、同节多个所有者、父子节重叠均拒绝。根模型拥有整个文件，因此不能同时注册另一个子节模型。多个上下文可贡献不重叠的声明，不自动选择其他上下文。

`Save` 替换模型拥有的完整部分，其他节保留；根模型保存替换整个文件根内容，根模型 `Reset` 清空持久化覆盖，再恢复默认值。文件缺失时读取与重置均不创建文件。需要多个模型分别保存时，使用互不重叠的节声明。

## 4. 读写 API、提交与原生读取视图

以下文件与类型读写 API、Configuration / Options 投影和变化通知已在四种格式路径实现。文件入口与类型服务使用相同的操作名称和语义。

### 4.1 文件与类型入口

`ConfigurationFile` 通过 `new ConfigurationFile(context, path: ..., options: ...)` 创建，日常使用只需上下文。`contexts` 集合重载合并多个上下文，两种形式共用同一文件实现。构造校验并固定路径、选项、静态声明及模型元数据，不进行文件或密钥 I/O。

`ConfigurationFileOptions` 是普通可选设置类型，各创建和注册入口共用：

| 设置 | 默认与用途 |
| --- | --- |
| `Format` | 未指定；按扩展名选择，默认文件采用 JSON |
| `Encoding` | UTF-8 无 BOM；设置文件输出与无 BOM 输入的编码，Unicode BOM 输入优先，规则见第 5.4 节 |
| `Protection` | `Auto`；Windows DPAPI，macOS / Linux 自动 AES；可显式选择 `Dpapi` 或 `AesGcm` |
| `EncryptionKey` | 未指定；应用提供稳定的 32 字节 AES 密钥，组件复制使用 |
| `KeyFilePath` | 未指定；自动 AES 使用组件默认位置，可覆盖为自定义路径 |
| `ProtectPlaintextOnLoad` | `true`；加载已有明文时自动保护；关闭后加载不回写，显式写操作仍保护 |
| `Protector` | 未指定；借用应用的 `IConfigurationProtector` |

选项在构造或注册时固定，后续修改不影响已有实例。密钥来源及互斥组合见第 6.2 节。`Path` 和 `KeyFilePath` 暴露实际固定位置，后者仅在自动 AES 模式有值。

文件实例直接提供以下操作。异步读取返回 `Task<T>`，其余异步操作返回 `Task`；异步入口最后一个参数均为可选的 `CancellationToken cancellationToken = default`，表中省略该参数：

| 同步入口 | 异步入口 | 语义 |
| --- | --- | --- |
| `Read<T>()` | `ReadAsync<T>()` | 首次加载并自动保护文件明文，随后返回最近成功加载或提交的独立模型副本 |
| `Save<T>(T value)` | `SaveAsync<T>(T value)` | 完整替换该类型拥有的配置节，保留其他配置节 |
| `Update<T>(Action<T> update)` | `UpdateAsync<T>(Action<T> update)` | 在文件协调范围内读取最新值，执行一次同步修改并保存 |
| `Update<T>(Func<T,T> update)` | `UpdateAsync<T>(Func<T,T> update)` | 在相同协调范围内执行一次同步变换，保存返回的新模型，支持 `record/init` |
| `Reset<T>()` | `ResetAsync<T>()` | 删除该配置节的持久化覆盖，恢复模型默认值 |
| `Reload()` | `ReloadAsync()` | 明确重读整个文件并自动保护明文，成功后更新快照和已接入的读取视图 |

首次 `Read` 或 `ReadAsync` 以文件为单位加载、恢复受保护值、自动保护声明范围内的普通明文并建立快照；文件不存在时建立默认快照，不创建文件或目录。加载或自动保护提交失败不标记为已加载，已有快照保持不变。需要写回时，提交前接受取消，提交后发布结果且不再报告取消；无需写回时在发布前接受取消。加载成功后，读取只取得已发布快照的副本，不再次访问文件或密钥设施；`ReadAsync` 可以返回已完成的任务。外部文件变化通过 `Reload` 或 `ReloadAsync` 获取，不增加缓存时长选项或后台监听。

`Save`、`Update` 和 `Reset` 可以作为第一个操作，直接复用第 4.2 节所需的最新文件读取，不要求应用先调用读取或初始化方法。`Reload` 和 `ReloadAsync` 也可作为提前加载入口，供启动集成复用。

`ISettings<T>` 是供 DI 使用的类型服务，提供相同的 `Read`、`Save`、`Update`、`Reset` 同步与异步方法；`T` 已由服务类型确定，调用方法时无需再写类型参数。它委托同一个文件实例，不另建缓存、文件锁或生命周期；整文件重载由 `ConfigurationFile` 负责。直接使用文件实例不必先取得类型服务。

`ConfigurationFile.OnChange<T>(Action<T>)` 与 `ISettings<T>.OnChange(Action<T>)` 提供直接订阅，均返回用于退订的 `IDisposable`，无需接入 Options。订阅只接线，不加载文件、不立即回调；普通首次读取也不通知。本实例成功保存、更新、重置或显式重载后，每个订阅者获得当时最新模型的独立副本。同一文件其他节的提交也会触发，不比较值或属性差异；没有产生文件写入的成功重置也按快照发布通知。回调同步执行，不使用 `async void`；需要后续异步工作时由应用调度并管理失败。释放订阅不等待已经开始的回调，文件释放前由订阅者完成退订。

修改读取副本不改变共享状态，也不自动保存；调用方不在保存期间并发修改同一输入对象。`Update` 的 `Action<T>` 回调修改副本，`Func<T,T>` 回调返回要保存的非空模型；两者均只操作内存，不执行 I/O、不使用 `async void`，也不重入同一文件的读写、重载或释放。回调抛异常、返回 `null`、校验失败或提交前取消均不提交，不自动重试回调。更新回调与变更通知均不保证在原调用线程或 UI 线程执行；界面通过自己的调度器更新控件。

`Save` 允许最后一次完整编辑结果覆盖同一配置节的先前值，不自动合并两个旧编辑副本。需要基于当前值修改个别字段时使用 `Update`。配置不能为用户界面的业务编辑冲突做隐式决定。

已加载的文件被外部删除后，普通读取仍返回原快照；显式重载成功后采用模型默认值并通知，不重新创建配置文件，也不修改调用方先前取得的副本。

同步入口使用同步 I/O 与等待，异步入口使用可用的异步 I/O 与可等待协调；两者共享状态、模型转换、保护和提交规则。不用 `.Wait()`、`.Result`、`GetAwaiter().GetResult()` 桥接整条异步路径，也不用 `Task.Run` 包装同步读写。内存转换、加密计算和原生文件提交按其实际能力执行，不把它们全部声明为可中断的异步操作；平台调用的阻塞与取消边界随实现验证说明。

### 4.2 文件级提交

所有模型的同步与异步写入遵守同一条提交规则：

1. 进入当前文件实例的协调入口，再取得同一路径的跨进程写入互斥。
2. 在协调范围内重读最新格式文档，建立本次读取数据，保留非目标配置节的原生节点和已有密文。
3. 从目标模型构造完整配置节点；`Update` 使用本次重读的值执行修改，`Reset` 移除目标配置节。
4. 准备整份候选快照，应用默认值并执行业务校验，建立已启用的读取投影；通过后保护目标模型节点，并保护其他所选声明位置的原有明文，保留其已有密文与非目标数据，完成格式可表达性校验与文件输出准备。所有修改合并为一次提交，不先为加载保护写一次文件。
5. 写入同目录的本次独占临时文件，完整写入并关闭。
6. 检查提交前取消，再替换或移动为目标文件；该操作是提交点。
7. 发布与提交结果一致的快照，释放实例协调及跨进程互斥后，再通过同一个变化令牌通知直接订阅和原生读取消费者。

候选内存状态和必要的读取投影应在提交前准备好，提交后不再依赖可能失败的重新解析。消费者通知不在文件写入锁内执行，避免消费者重入或耗时操作占用提交锁；通知读取当前已提交视图，不承诺逐个交付并发提交期间的中间值。若通知消费者失败，文件已经提交的事实不能被改写为未保存或已回滚；通知错误由诊断边界单独处理，不重新执行更新回调。

通知使用文件级原生变化令牌，不维护属性差异或通知队列。`Confio-Configuration` EventSource 的事件 `1` 报告通知失败，事件 `2` 报告启动失败清理中的附加错误；只包含异常类型，不输出业务校验消息、异常正文、配置键或值。最终日志建立前的加载错误仍直接交给启动调用方。

提交前的序列化、业务校验、加密、写入或替换失败，不发布候选快照，不改变变化令牌，不覆盖原始故障；只清理本次创建的临时文件。Windows `1176/1177` 表示替换失败后文件状态可能已改变，此时保留剩余替换文件，在原异常 `Data["Confio.ReplacementFile"]` 中提供原临时路径供检查，不声称磁盘已回滚。按照平台契约，替换文件仍保留原临时名称；当前未指定备份文件，`1176` 下旧文件已不存在，`1177` 下旧文件仍存在但已改名。提交之后不再因迟到的取消报告本次保存被取消。文件完整替换不等于文件系统断电事务。

`Reset` 的目标覆盖不存在且其他声明位置没有待保护明文时，跳过文件写入，从本次读取数据发布当前快照；文件也不存在时采用默认值。此时按无需写回的快照发布规则处理取消，不为删除一个不存在的覆盖创建配置文件。

### 4.3 并发与外部编辑

独立应用可能同时运行多个实例；多个模型共用一个文件后，进程内按模型加锁已不足以避免覆盖。目标是让同包消费者对同一规范化路径使用文件级跨进程互斥，并在锁内完成重读、修改与提交。具体互斥机制要通过目标平台验收，不提前宣称某个 Windows 实现覆盖所有平台。

当前写入互斥使用目标旁的 `<文件名>.confio.lock`，以独占文件句柄协调同包进程；句柄关闭或进程退出即释放，不删除锁文件以免其他进程锁住不同文件实体。锁竞争按平台错误码识别：Windows 为 `32/33`，Linux 的 `EAGAIN/EWOULDBLOCK` 为 `11`，macOS 为 `35`。只有真实竞争采用短间隔等待；同步入口等待到锁释放，异步入口还可通过已有 `CancellationToken` 取消，不设置隐式超时或要求应用重试。权限、路径等其他错误直接报告。取得锁后才重读最新文件并执行本次更新回调，业务回调不重试。

提交使用独占同目录临时文件，刷新并关闭后通过 `File.Replace` 或首次 `File.Move` 提交；异步数据传输可等待，磁盘刷新和替换是同步平台调用。各平台的文件互斥、替换及失败路径证据见第 8.1 节，已验证的本地文件系统不代表其他文件系统与权限组合。

Windows 提交遇到共享冲突 `32/33` 或无法删除被替换文件 `1175` 时，只重试同一份已写完的临时文件，最多额外尝试 4 次，每次等待 25 毫秒。异步等待接受取消，每次再次提交前检查取消；不重新解析、加密、执行业务更新回调或提前通知。达到上限或发生其他错误时报告；除第 4.2 节的部分替换失败外，清理本次临时文件。可能已移动文件的 `1176/1177` 不重试。保留 `File.Replace` 的目标文件元数据处理，不使用删除原文件再写入、覆盖式移动、吞异常或无限重试规避失败。该处理针对实际复现的短暂失败，不宣称能修复文件系统故障或持续占用。

上述错误码的文件状态以 [Windows ReplaceFile 返回值](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew#return-value)为依据。`1175` 保留两个文件原名，因此可以重试；`1176/1177` 可能改变文件位置，按第 4.2 节保留现场。

同一实例的首次加载、`Save`、`Update`、`Reset` 和 `Reload` 及其异步形式共用实例内协调入口，范围覆盖读取、候选快照准备与发布。首次读取进入协调后重新检查是否已有快照，避免同步与异步调用重复初始化或用旧数据覆盖后续提交。加载后的普通读取只取得一个已发布快照，不进入文件 I/O 协调。

`Reload` 重新读取文件；发现声明范围内的普通明文时，取得文件互斥并重读最新文档，在同一次提交中自动保护后再发布整份快照。候选准备、保护或提交失败保留旧快照；取消边界与首次加载相同，提交成功后不再报告取消。发布后按第 4.2 节的通知规则处理。这样不会出现重载先读到旧文件、保存发布新值后重载又覆盖回旧值的情况，也不需要增加版本冲突协议或重试队列。

该保证限于遵守同一提交协议的消费者，不承诺与任意文本编辑器并发修改时自动合并。另一进程的修改也不会自动刷新当前进程的旧快照；显式重载或本实例下一次成功的协调提交更新本实例视图。

默认不建立后台监听。本实例成功提交或重载会发出变化通知，直接订阅与原生读取复用同一令牌；外部修改始终走同一文件级重载入口。

`ConfigurationFile` 实现 `IDisposable`，同步与异步消费均可使用普通 `using`。文件流和每次操作取得的资源在该操作结束前完成清理；调用方在全部读写完成后释放实例，不将释放与读写并发执行。`Dispose` 只释放实例拥有的同步资源，不隐式保存，也不阻塞等待未完成的异步操作。已释放实例拒绝后续操作。不为了异步读写额外要求 `IAsyncDisposable`。

直接创建的实例由创建方释放。第 4.5 节中由容器工厂创建的实例由根容器释放，外部实例重载始终保留调用方所有权，不提供所有权切换参数。原生接入自行创建的实例按第 7.5 节交由配置源管理，随 ConfigurationManager 或 Host 释放。Provider 直接提供文件的投影和令牌，不持有缓存或订阅；订阅由原生配置根及 Options Monitor 释放。各类型服务不持有可释放资源，不释放共享文件；业务服务也不对注入的文件实例使用 `using`。

### 4.4 与 Configuration、Options 的关系

本节通过第 7.5 节的原生注册入口实现；普通 DI 注册按第 4.5 节保持首次读写加载。

Configuration 索引器和 Options 属性通过同步调用取值，因此原生接入在消费者构造前建立可读快照。第 7.5 节的启动入口完成同步加载或等待异步加载，已有成功快照时直接复用；属性读取和 Options 工厂只消费内存状态。普通类型读写按第 4.1 节首次读写加载。

Confio 的 Configuration Provider 提供同一份成功加载或提交数据的已解密读取投影。已声明配置节根据采用模型默认值后的快照投影，未声明部分根据文件数据投影，不推断未选择模型的默认值。扁平键值视图按原生 Configuration 的表达范围提供读取，不能完整保留对象、数组等类型信息；类型化读取直接使用模型快照。

JSON 投影使用大小写不敏感的 `:` 路径、从 `0` 开始的数组索引和不依赖区域的标量文本；空对象及 `null` 投影为 `null`，空数组投影为空字符串，沿用 .NET 10 JSON Provider 的表达规则。模型节点和投影存于同一发布快照。只有接入原生读取时才生成投影；扁平键冲突在接入或后续提交前拒绝，保留原文件与旧快照，不额外限制只做类型读写的合法 JSON。

Provider 首次 `Load` 复用启动入口的预加载快照；后续 `IConfigurationRoot.Reload()` 调用同一个 `ConfigurationFile.Reload()`，重新读取文件、校验并自动保护明文。异步重载继续通过 `ConfigurationFile.ReloadAsync()`。失败保留文件实例原有的成功快照，不发布本次 Confio 变更；原生根包含多个 Provider 时不承诺整体回滚。原生根沿用自身的通知行为，不保证单次重载只发出一次根通知；不额外建立去重队列、投影缓存或文件监听器。

接入已有 Configuration 或 Host 时，组合根按原生 Provider 优先级取值；Confio 的文件读写及默认 Options 的初始数据仍来自选定文件。例如文件的 `Mail:Port` 为 `465`，更高优先级 Provider 提供 `2525`，则组合根返回 `2525`，文件读取返回 `465`，Confio 的 Options 工厂以 `465` 为初始值再执行应用配置流程。其他配置源的覆盖不自动写回文件；应用需要的业务覆盖通过原生配置流程表达，不增加隐式合并或来源切换机制。

业务修改通过明确的保存 API 持久化；加载时的明文保护写回由文件运行库承担。文件 Provider 不把 `Set` 或 `IConfiguration` 索引器赋值解释为自动保存；拒绝不受支持的写入，不靠“解密后调用底层 Set”发布内存数据。这样不会出现解密 Provider 与可写 Provider 叠加后将明文回写磁盘的路径。

选择原生读取接入后，Confio 为所声明模型提供默认命名 Options 接入：组件内复用一个泛型 `OptionsFactory<T>` 子类，在 `CreateInstance` 中为 `Options.DefaultName` 取得同一模型快照的副本，随后执行原生 `Configure/PostConfigure/Validate` 流程。其他名称使用模型构造默认值及原生配置流程，不隐式映射为同一持久化配置节。所选静态声明通过共享注册流程补齐类型服务、工厂及变化令牌接线，应用不逐模型调用 `Bind` 或注册工厂。

读取副本与原生 Options 缓存分别遵守以下语义。表中的 Options 属性均读取默认名称：

| 读取入口 | 对象与刷新规则 |
| --- | --- |
| 文件或 `ISettings<T>` 的 `Read` / `ReadAsync` | 每次从当前成功快照取得独立副本 |
| `IOptions<T>.Value` | 首次成功创建后复用缓存，保存或重载不刷新该缓存 |
| `IOptionsSnapshot<T>.Value` | 同一作用域首次取值时创建并缓存；已缓存的值在该作用域内保持，新作用域在首次取值时取得当时的快照 |
| `IOptionsMonitor<T>.CurrentValue` | 复用默认名称的缓存；Confio 的变化令牌使该缓存失效并重新创建 |

Options 对象按原生机制缓存和共享，消费方将其用于读取；需要编辑时使用 `Read` 或 `ReadAsync` 取得副本。刷新不会逐属性改写已经交给调用方的旧对象，也不保证已有 Options 缓存与最新文件读取始终相等。变化来源遵守第 4.3 节，外部编辑需要显式重载。

预加载完成文件解析、保护恢复、模型业务校验和快照建立，Options 配置与校验仍遵守原生创建和 `ValidateOnStart` 时序。`Configure/PostConfigure` 的调整不自动持久化，也不改变文件快照；后续 Options 校验失败不回滚已经完成的保存。注册遵守开发规范的显式服务优先规则，应用显式替换某类型的工厂时，由该工厂承担 Options 创建职责。

依据：[原生配置源取值顺序](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Configuration/src/ConfigurationRoot.cs)、[JSON 投影](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Configuration.Json/src/JsonConfigurationFileParser.cs)、[OptionsFactory 扩展点](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Options/src/OptionsFactory.cs)、[默认 Options 缓存](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Options/src/UnnamedOptionsManager.cs)、[作用域 Options 缓存](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Options/src/OptionsManager.cs)及[Monitor 缓存与通知](https://github.com/dotnet/runtime/blob/v10.0.0/src/libraries/Microsoft.Extensions.Options/src/OptionsMonitor.cs)。Confio 的默认接入直接消费静态模型快照，不经过 `ConfigurationBinder` 再绑定，也不依赖另一个生成器处理 Confio 生成的绑定调用；本项目实际平台证据见第 8.1 节。

### 4.5 普通容器注册

`services.AddConfigurationFile(context, path: ..., options: ...)` 返回原生 `IServiceCollection`。多个上下文使用集合重载；选项、密钥输入和所选声明在注册时固定。声明生成已知模型的封闭泛型注册，应用不逐模型编写工厂，也不执行运行时模型扫描。

每个注册文件由容器的单例工厂创建和释放；所属模型的 `ISettings<T>` 也是单例，只转发到该文件，不维护独立缓存、锁或资源。构建根容器及解析这些服务不做文件或密钥 I/O，首次明确读写负责加载。业务构造函数只保存依赖；不同作用域共享同一注册文件，释放作用域不释放文件。

不同模型可分别注册到不同文件。每个 `ISettings<T>` 必须解析自己的文件，不按最后注册的文件推断归属。同一模型在一个服务集合中重复归属时明确报错，即使路径相同；需要同模型的多个文件时直接创建文件实例。单文件应用可以注入 `ConfigurationFile`；多文件应用使用类型服务或 `IEnumerable<ConfigurationFile>`，单值解析遵守原生 DI 的最后注册规则。单个文件内部的节冲突按第 3.3 节检查。

`ISettings<T>` 是可替换的默认服务，使用 `TryAddSingleton` 保留应用显式注册，后置替换遵守原生规则。替换类型服务不转移文件归属，也不隐式改变 Options 的数据来源。

`services.AddConfigurationFile(file)` 借用已有实例，从它的固定声明注册类型服务，不再提供另一组上下文或路径。容器不释放外部实例，调用方让它存活到所有操作和使用方结束。组件不通过工厂包装外部实例改变其所有权。

普通注册不添加 Confio 的 Configuration 投影或 Options 工厂，也不要求 Host。需要这些同步读取视图时选择第 7.5 节的预加载接入，不先对同一模型做一次普通注册。组件不创建临时容器或全局按路径共享表，应用在组合根调用原生 `BuildServiceProvider()`。

生命周期及默认注册依据[原生 DI 指南](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection-guidelines)。

### 4.6 模型业务校验

配置节根模型可选实现 `IValidatableSettings.Validate()`。应用在此声明字段范围、跨字段关系以及需要检查的嵌套对象；普通模型不需要空实现，不增加验证器注册或逐类型接线。运行库通过接口直接调用，不扫描 DataAnnotations 属性或反射遍历业务对象图。

校验针对已完成默认值应用和保护恢复、能按静态元数据读取的模型。首次加载、重载和每次提交准备都会校验所选声明的整份候选快照；只保存一个节，也不能发布其他已声明节无效的快照。`Update` 先加载并校验最新文件，再执行一次业务回调，随后校验修改后的候选结果。普通 `Read/ReadAsync` 从已发布快照返回副本时不重复校验。

规则不满足时由模型抛出原生 `ValidationException`；校验异常原样交给调用方，文件与最近成功快照保留，不通知订阅者。加载失败后仍可再次加载；`Save/Reset` 可显式替换目标节的无效数据，但不能修复无法解析的整份文件，也不能跳过其他声明的校验。`Reset` 校验恢复后的默认模型，默认值无效时同样拒绝发布，包括不存在文件的情况。

校验方法是同步、只读的业务规则，不修改模型、不执行 I/O、不依赖业务 DI，也不重入文件操作。异常消息描述规则，避免包含配置值；组件不记录业务校验异常正文。模型内规则由应用管理，组件负责在所有消费入口的一致位置执行。

此契约负责文件及其共享快照。原生 `Configure/PostConfigure` 后的 Options 视图由原生验证器检查，不自动将其检查注册成文件规则，也不在该阶段重复执行持久化校验。涉及环境、服务状态或业务资源的检查仍属于应用启动与使用逻辑。

### 4.7 错误处理与功能边界

组件负责正确读写配置并明确报告失败。错误处理复用现有读写入口：

| 情况 | 组件行为 | 后续操作 |
| --- | --- | --- |
| 文件不存在 | 使用模型默认值，读取不创建文件 | 修改模型后显式保存 |
| 待保存模型校验失败 | 拒绝提交，保留文件与生效配置 | 修改输入值后重新保存，不把它当成文件损坏 |
| 候选值超出格式表达范围 | 格式适配抛出 `ConfigurationValueException`，提供格式、属性路径与原因；拒绝提交，不改变文件、快照或通知状态 | 根据实际原因修改输入，或选择能表达该模型数据的格式；应用无需复制格式检查 |
| 文件语法损坏 | 加载报错，保留原文件和已有成功快照 | 修正文件后重载 |
| 密钥缺失、密文篡改或解密失败 | 报告失败，不替换密钥或回退默认值 | 提供正确密钥或修正配置后重新加载 |

文件协调、临时文件提交、取消与失败清理由组件承担，具体遵守第 4.2、4.3 节。保留失败现场属于读写可靠性，不意味着提供备份恢复功能。

不设计备份恢复 API、历史轮换或后台恢复，也不要求应用为正常读写补充这些流程。Sample 的“还原演示文件”只撤销它自己制造的损坏，不代表组件能力或后续实施任务。

## 5. 多格式、类型与依赖

### 5.1 共享模型转换

文件处理区分格式文档与模型转换节点。格式文档复用各格式的现成文档模型或必要的键值结构，保留原生标量类型、非目标配置节及其密文；模型转换节点优先复用 `JsonNode`，用于已声明配置节的类型转换、保护与读取快照。两者由同一文件责任方处理，不建立公共节点框架或另一套文件缓存。保存只把目标配置节转换后合回最新格式文档，不从模型快照重建整个文件。

JSON 与受支持的 YAML Core 数据均可由 `JsonNode` 无损承载，因此复用这一结构表示文件文档。YAML 适配只归一标量词法，不把数值统一转换为 `double`；输出时保持字符串、数值、布尔和空值的区别。TOML 在一次操作内保留原生 `TomlTable` 文档；INI 保留解析后的字符串树，仅在读取所选声明时恢复类型。内部文档边界负责投影、目标节替换、保护位置写回和编码，发布的文件快照仍只有共享模型节点，不建立第二份长驻文件缓存。

应用模型的序列化与反序列化统一使用 `System.Text.Json` 的静态元数据，YAML/TOML 库不分别绑定业务对象。节点归一和路径解析复用所选上下文的 `JsonTypeInfo` / `JsonPropertyInfo`，包括集合元素、字典键、成员所属类型与构造参数关联。最终 JSON 名称仍按所选上下文确定，Confio 生成器只补充配置声明、保护与默认构造接线，不反射重建业务模型，也不生成另一套序列化元数据。

格式解析使用已知的节点和容器类型承载可变的文件结构，不要求为每份文件生成 CLR 类型。应用模型的构造与成员访问来自所选静态元数据，所有支持目标沿用同一规则；不按运行时或发布方式切换到另一套反射序列化器。

常规标量、枚举、日期时间、可空值、嵌套模型、集合和字符串键字典的转换由组件的统一规则负责，不要求应用按每个属性、每种格式编写转换器。数值不得因统一转为 `double` 而丢失精度，机器表示使用固定区域规则。超出支持范围的类型与转换器必须明确诊断，不能落入反射备用路径。

模型与上下文采用以下固定约定，普通应用的原生上下文默认满足，不增加一组 Confio 序列化配置项：

- 配置节根模型是可直接无参调用构造函数的具体引用类型，支持公开无参构造或全部参数具有默认值的构造；不能要求调用方补充必填构造参数或 `required` 成员赋值。上下文提供读写所需的静态元数据，不能只提供快速序列化输出。嵌套对象需要用缺失的 `init` 成员默认值时，也须能默认构造；原生标记为必填的成员仍由原生元数据检查，不隐式补齐。
- 模型成员使用确定的 CLR 类型，不接受 `object` / `dynamic` 或多态元数据在运行时选择另一套成员，以免遗漏实际类型上的保护声明；任意 JSON 数据直接使用 `JsonNode` 或 `JsonElement`，无需另写转换器。
- 持久化成员完整输出，保留显式 `null`、零值及空容器。`DefaultIgnoreCondition` 使用 `Never`，非持久化成员用原生 `[JsonIgnore]` 排除；显式 `[JsonIgnore(Condition = Never)]` 与默认完整输出同样支持。属性级条件及原生序列化回调按应用显式选择执行，不因存在回调就拒绝；被条件省略的成员再次读取时采用默认值，应用需要完整往返时不设置省略条件。
- 对象与集合使用 `Replace` 语义，不接受 `Populate` 改变配置读取行为。命名策略及 `[JsonPropertyName]` 可以使用，读取归一、写入和保护均依据最终序列化名称，模型属性匹配遵守 `PropertyNameCaseInsensitive`，字典键仍区分大小写。INI 在格式适配中按本方言匹配名称，并拒绝无法无损保存的大小写冲突；原生 Configuration 的扁平键冲突只在投影边界拒绝。
- 自定义转换器需要静态可调用、可往返，并符合选定格式的表达范围；无法确定其节点形态时不承诺跨格式适配。转换器改变受保护后代的节点结构时拒绝该声明；整体保护转换结果则按同一保护边界处理。

保护声明同时携带可达的外层类型，用于拒绝属性转换器或上下文转换器遮蔽受保护后代的情况。同一子类型在别处已成功映射，不能使另一条被转换器遮蔽的路径漏过检查；该信息只描述保护覆盖范围，不生成另一套完整模型结构。普通应用仍只声明模型和 JSON 上下文。

声明中的冲突尽量由生成器定位；依赖最终上下文选项或元数据才能判断的限制，在文件实例构造或注册边界一次性检查并固定结果。运行中的文件输入与保存值仍在各自转换边界校验，不在每次读取时重复检查声明，不通过往返比较整个对象图来代替明确规则。

### 5.2 格式表达边界

| 格式 | 目标配置语义 | 必须明确的边界 |
| --- | --- | --- |
| JSON | 对象、数组、标量、`null` | 保留数值精度，区分缺失、显式空值与空容器；文档与保护载荷读写统一限制为 64 层，包含配置节外层，过深写入在提交前失败 |
| YAML/YML | YAML 1.2 Core 的字符串键映射、数组、标量、`null` | 使用下述固定规则；保留数值精度，不据标签创建 CLR 类型，别名展开为独立值 |
| TOML | TOML 1.1 的表、数组和常规标量 | 没有原生 `null`；原生日期与普通字符串保持不同类型，进入模型时按声明的 CLR 类型转换；所有目标采用同一语法版本 |
| INI | 配置节、字符串键值、层级对象、非空数组及字符串键字典 | 使用下述固定方言与类型归一规则；不把所有字符串猜测为数字或布尔值 |

JSON 内部输出使用 UTF-8 和带缩进的标准写入器，再由第 5.4 节的文件编码边界处理落盘字节。统一允许常用 Unicode 文本直接输出；中文、日文及重音字母可直接阅读。引号、反斜杠、控制字符及编码器仍需转义的字符遵守标准 JSON 规则，不要求应用配置 encoder。敏感节点继续先加密再写入，读取与密文协议不因文本可读性设置改变。

YAML 使用 [YAML 1.2.2 Core Schema](https://yaml.org/spec/1.2.2/#1032-tag-resolution)，固定约定如下：

- 输入为单个 Unicode 文档，支持 UTF-8、UTF-16、UTF-32，编码与 BOM 规则见第 5.4 节；根必须是映射。空文件、根 `null`、多个文档和显式指定其他 YAML 版本均失败。输出使用所选编码、LF。
- 普通标量按 Core 规则解释空值、布尔、十进制整数、`0o` 八进制、`0x` 十六进制和小数／指数。任意精度的文件数值按词法保留，进入模型时再遵守其 CLR 类型范围；`.inf` / `.nan` 明确拒绝。
- 引号中的值是字符串；`yes`、`on`、日期、`0b10`、`1_000` 等不匹配 Core 数值或布尔规则的普通值也是字符串。`00123` 是整数，需保留前导零时写为 `'00123'`。日期字符串可按模型的 `DateOnly`、`DateTimeOffset` 等静态元数据转换。
- 支持 `!!str`、`!!null`、`!!bool`、`!!int`、`!!float`、`!!map`、`!!seq` 及非特定标签 `!`；标签与节点必须匹配，不支持自定义标签或 `!!timestamp`。不调用 YAML 对象反序列化器。
- 映射键必须解析为字符串，区分类型的数字、布尔和空键需要加引号。键名忽略大小写后仍须唯一。`<<` 是普通字符串键，不应用 YAML 1.1 的合并键规则。
- 别名只能引用先前已完成的锚点，读取后展开为独立值；拒绝循环及前向引用。文档及展开后的容器深度最多 64 层，整份文档的别名累计展开最多 100000 个值节点，在复制前检查。
- 保存使用现成 YAML 输出器；会重新选择缩进与引号，显式转义换行以保留字符串和字典键内容，不保留注释、标签或锚点的原始写法。

TOML 统一采用 [TOML 1.1](https://toml.io/en/v1.1.0)。复用 Tomlyn 2.10.1 的严格语义校验和库内固定 `TomlTable` 源生成上下文进行读写，应用模型仍走共享 JSON 静态元数据，不要求应用提供 TOML 上下文。固定节点转换会覆盖内联表重复键，因此读取先执行上游语义校验，再转换节点；不在 Confio 重写 TOML 校验器。输入为 UTF-8，可带 BOM；空文档表示没有持久化配置。表键在 Confio 中忽略大小写后须唯一，文档容器深度最多 64 层。固定规则如下：

- 原生整数使用有符号 64 位，原生浮点使用有限 binary64；`inf` / `nan` 拒绝。保存整型超出范围，或数值通过 binary64 后不能保留其 JSON 数值含义时，在写盘前拒绝，不把高精度 `decimal` 偷偷改为近似值。精确十进制数据超出此范围时应选择 JSON / YAML / INI，或由模型明确声明字符串语义。
- 原生日期与外观相同的字符串保持不同类型；读取投影把日期转换为规范文本，再由静态模型元数据转换。保存内置 `DateOnly`、`TimeOnly`、`DateTime`、`DateTimeOffset` 时写原生日期，字符串属性保持字符串。日期时间使用 .NET 的七位小数秒精度；自定义转换器输出的文本仍服从其自定义表示。
- 支持空表、空数组、多行字符串；没有原生 `null`。保存其他配置节不会改变未修改表中的日期、字符串或已有密文。输出不保留原注释、引号风格或表的排版。
- 支持点分键、引号键、内联表与表数组，以及 TOML 1.1 的 `\e`、`\xHH` 转义、多行和末尾逗号的内联表、省略秒的时间。保存采用统一规范写法，保持数据含义；错误只包含必要的行列信息，不输出配置正文，失败保留文件和成功快照。

INI 以原生 Provider 的行、注释、节名、键值和外层双引号规则为基础。默认使用 UTF-8，可显式选择 GBK 等编码，BOM 规则见第 5.4 节；空文档表示没有持久化配置。节头只确定键前缀，不声明空对象；层级分隔使用 `:`，数组采用从 `0` 开始的连续索引，不接受缺口或 `00` 之类的别名索引。路径深度最多 64 层，键名忽略大小写后唯一，标量路径不能同时拥有子键。

输出使用顶层节头及以 `:` 分隔的相对键；全局标量先于各节输出。路径段不得为空、有首尾空白或含 `:`、`=`、CR、LF；实际输出键不能以 `;`、`#`、`/`、`[` 开头。字符串只在需要保留首尾空白或字面双引号时增加一对外层引号，空字符串写成 `Key=`。显式 `null`、空容器、多行值及无法按该方言往返的键，在写盘前拒绝，不以省略或隐藏 JSON 载荷替代。Reset 删除最后一个键后移除仅用于路径的空父节点，不把节头当成空对象保存。

这些是 Confio 选定的 INI 方言边界。INI 没有统一的值类型标准；本项目保持上述明确规则，不增加私有 null、空容器或多行转义协议。

INI 解析结果先保留为字符串，组件依据同一静态模型元数据完成受支持标量的归一，再交给 JSON 模型转换。例如整数 `Port=587` 进入数值节点，字符串 `Code=00123` 保留前导零，字符串 `Enabled=true` 仍是字符串；枚举按上下文的数值或名称规则处理。未声明部分保持字符串语义。普通应用不增加数值处理特性、布尔转换器或逐属性映射；需要从 INI 明文标量恢复、又不能确定转换规则的自定义类型，在文件实例构造或注册边界报告为不支持。已解密节点直接按其恢复的类型进入共享模型转换。

INI 支持内置数值、布尔、枚举、字符串、字符、日期时间、`TimeSpan`、`Guid`、`Uri`、`Version` 与 Base64 字节数组。命名浮点文本等特殊输入仍由模型的原生 JSON 选项决定是否合法；不把普通字符串猜成数值。任意 `JsonNode` / `JsonElement` 或其他自定义明文标量不推测结构；整体保护后的载荷可以使用这些类型，解密结果不再经过 INI 词法恢复。

格式选择不改变模型的业务语义，但不能承诺任意模型在所有格式间无损切换。例如属性默认值为非空字符串时，用户显式改为 `null`，不能在 TOML 中简单省略属性，否则重新读取后会恢复非空默认值。无法表达的候选值在写盘前拒绝，不偷偷删除或改写为另一种值。

可空类型可以正常声明，文件或属性缺失时仍按模型默认值读取；可表达性检查依据本次实际持久化值。例如 `string?` 属性当前为空字符串时可以保存到 TOML / INI，实际为 `null` 时才拒绝。不增加模型的逐格式副本、能力查询接口、应用预检查或保存前清洗流程。

格式适配识别到无法写入的候选值时使用 `ConfigurationValueException`（继承 `NotSupportedException`），与文件语法损坏、模型校验失败分开处理。其 `Format` 为文件格式名，`Reason` 为 `ConfigurationValueError`，`Path` 复用现有 JSON Pointer：从文件根开始，使用最终序列化名称，数组索引从零开始，路径段中的 `~` 与 `/` 分别转义为 `~0` 与 `~1`。例如 `/Mail/Password`、`/Mail/Endpoints/0/api~1key~01`。异常不包含配置值、数值原文或第三方内部异常；英文消息用于开发诊断，应用通过结构化属性生成自身提示，不解析消息文本。

可表达性校验针对保护后的实际持久化节点。非空的整体保护对象先变成一个密文字符串，因此内部可以含 `null`、空容器或超出格式范围的数值；受保护属性自身为 `null` 时仍不加密，继续受格式限制。自动保护只写回原文件中已有的保护位置，不把读取时补齐的默认属性或已解密的其他配置节写回。Save / Reset 可以替换语法有效但模型值无效的目标节；Update 必须先成功读取并校验最新值。

默认保证受支持配置数据和未修改配置节的语义，不保证注释、缩进、引号风格和节点顺序的逐字保留。不为了统一所有格式发明隐藏 JSON 子协议或通用无损文档编辑层。

例如更新 `Mail` 时，另一 TOML 配置节中的原生日期与外观相同的字符串须保持各自类型，未修改节中的密文也继续作为密文写出。它们不能因经过公共 JSON 节点或已解密读取投影而改变持久化含义。

### 5.4 文件编码

`ConfigurationFileOptions.Encoding` 使用标准 `System.Text.Encoding`，默认严格 UTF-8 无 BOM。入口复制编码并启用编码、解码异常回退，固定字符集、前导标记和无损读写要求；不修改调用方对象，不沿用有损替换策略。后续选项变化不影响既有实例或 DI 注册。显式 `Encoding.Default` 遵守 .NET 原生含义：Framework 为系统活动代码页，现代 .NET 为 UTF-8，不作为跨平台库的默认选择。

文件输入先识别 UTF-8、UTF-16 LE/BE、UTF-32 LE/BE 的 BOM；存在时以 BOM 为准，无 BOM 时使用配置编码，不猜测代码页。保存以所选编码及其 `GetPreamble()` 为准，包括首次加载或重载触发的明文自动保护；不记忆并继承原输入编码。例如默认读取 UTF-16 BOM 的 JSON 后，写回使用 UTF-8 无 BOM。

JSON 允许显式编码供本地封闭用途使用，对外交换采用 UTF-8；YAML 使用 UTF-8、UTF-16、UTF-32；TOML 使用 UTF-8；INI 支持所选编码。格式不接受的编码在构造或识别输入 BOM 时抛出 `NotSupportedException`。无效字节和无法表示的实际输出字符抛出不含配置原文及内部异常的 `InvalidDataException`。编码完成后才进入文件提交，失败不修改原配置文件或成功快照，不发布成功通知。错误编码若仍能合法解码，组件无法可靠识别，调用方须为无 BOM 文件提供正确编码。

磁盘编码在文件边界统一转换为格式层使用的无 BOM UTF-8；各解析器保留适合其库的字节或字符串处理方式。同步、异步、更新、重置和自动保护共用此边界，二进制密钥文件不经过文本转换，字段保护载荷仍为第 6.1 节的 UTF-8 JSON。代码页使用标准 Provider，无进程级注册副作用。直接创建、普通 DI 和原生接入使用同一固定选项，不增加编码枚举、策略接口或逐格式接线。

## 6. 字段保护、密钥与失败

### 6.1 保护语义

`[Protected]` 声明持久化保护，可以作用于有静态元数据的字符串、值类型或整个子对象。成员由编译期声明识别，构造文件实例时依据最终 JSON 元数据固定实际节点路径；命名策略和 `[JsonPropertyName]` 不改变保护覆盖范围。声明被忽略或无法定位到实际输出节点时明确失败，不扫描业务类型补救。父节点整体保护时，其转换结果作为一个载荷，不再对内部成员重复加密。

保存时在内存中形成受保护节点的稳定表示，使用成熟的认证加密实现，再把密文表示交给格式适配。读取先恢复节点，再进行模型转换。四种格式共享保护机制，不按格式选择不同安全策略。

保护值采用固定规则，不要求应用配置“空值是否加密”：

| 节点状态 | 保存与密钥语义 |
| --- | --- |
| 缺失 | 读取时采用模型默认值，不取得密钥或补写文件，即使默认值非空；保存仍按完整模型的实际值处理 |
| 显式 `null` | 保持 `null`，不取得密钥；选定格式不能表达时仍明确失败 |
| 字符串 `""` | 保持空字符串，不取得密钥，不将空串改为缺失或 `null` |
| 非空字符串、值类型或非 `null` 子对象 | 整体保护后输出；空白字符串、空对象及只含默认值的对象也遵守此规则 |
| 已识别密文 | 读取时始终取得密钥并认证，即使解密结果是空字符串；失败不能套用空值规则 |

格式可表达性按保护后的持久化节点检查，未保护的值遵守原格式限制。组件不递归猜测一个非 `null` 子对象是否“尚未使用”；应用通过模型默认值表达实际状态。

密文使用明确标识和版本，不使用任意 CLR 类型名控制反序列化。保护用途绑定固定协议与逻辑字段位置，不把程序集名、文件路径或载荷自报用途作为解密条件。密文识别及节点恢复不依赖业务服务，使配置能在业务容器及最终日志建立前就绪。

四种格式的受保护值均采用 `enc:v1:<Base64>` 字符串。仅在所选上下文声明的保护位置，将大小写敏感的 `enc:` 识别为文件密文前缀；`v1` 是封装格式版本，后续内容是所选保护器输出的 Base64，不根据文本自动切换保护器。明文载荷是该节点的 UTF-8 JSON；保护用途固定为 `Confio/v1\0<JSON Pointer>`。模型成员使用最终序列化名称，字典键保留原始大小写，数组使用索引，路径转义 `~` 和 `/`。自动回写使用文件中的实际键名，避免属性匹配忽略大小写时留下旧明文。相同密钥与逻辑字段路径可跨应用、跨文件位置读取；移动字段会改变认证用途。未知版本、损坏载荷和认证失败均明确报错，不回退为明文。未声明或未保护的节点按普通配置数据处理，不因包含 `enc:` 或 `$confio` 而解密或拒绝，原生读取投影也遵守这一边界。

首次加载或显式重载时，受保护位置的普通非空字符串及明文子对象在整份候选校验成功后自动保护写回；已有有效密文保持不变。写回只修改文件中实际存在的保护位置，保留其他数据语义，不补写默认属性，不保证注释和排版。只有需要写回才取得文件互斥并重读最新数据，沿第 4.2 节提交路径写回成功后发布快照。文件只有有效密文时无需写权限；默认加载含待保护明文而无法写回时失败。`ProtectPlaintextOnLoad = false` 允许只读取明文，初次加载和 Reload 都不自动回写；显式 Save、Update、Reset 仍沿同一保护提交路径处理。

文件中受保护位置的 `enc:` 开头字符串始终按密文解析，包括首次读取。手写密码本身若以 `enc:` 开头，这种写法无法与密文区分，应通过模型 API 保存。`Save` 或 `Update` 的模型输入始终按明文处理，即使它是一段格式正确且可解密的密文文本，也作为完整的真实内容重新保护；读取只解密一层，不再识别解密结果的前缀。整体保护子对象时，内部字符串同样不再解释为独立密文。应用无需添加转义、首次运行标志或迁移步骤。

显式保存和重置可以替换语法合法文件中的坏目标配置节，其他配置节仍须可读且得到保留。生成声明支持有静态元数据的值类型整体保护，以及可空结构体中的成员保护。

除上述保留为空的状态外，受保护值持久化只输出密文，其明文不能进入组件写出的目标文件、临时文件、异常正文或日志。第三方解析异常可能包含原始行文本，适配边界需要保留安全的路径、位置和错误类别，避免默认诊断输出完整配置正文。

加密实现必须在支持矩阵的 Framework、现代 .NET JIT 与 Native AOT 中验证完整路径，使用成熟的认证加密或平台设施，不自研密码算法。必要的底层实现差异不改变配置文件与密文协议；同协议不等于跨用户或机器自动共享密钥。

保护和密钥访问同时服务同步与异步读写，不要求应用提供阻塞包装、异步桥接或默认密钥管理代码。平台设施实际支持的等待、取消和资源释放方式，在首条真实保护路径中验证并记录。

### 6.2 密钥默认与替换

各入口共用 `ConfigurationFileOptions`，保护方式在创建或注册时固定。枚举只选择 `Auto`、`Dpapi`、`AesGcm`；AES 的密钥来源通过 `EncryptionKey` 或 `KeyFilePath` 表达，不增加第二套算法模式或密钥提供器体系。

| 选择 | 行为 |
| --- | --- |
| 默认 `Auto` | Windows 使用当前用户 DPAPI；macOS / Linux 使用自动持久化密钥的 AES-256-GCM |
| `Dpapi` | 仅 Windows 可用，直接保护字段，不创建 AES 密钥文件 |
| `AesGcm`，没有指定密钥 | 在所有支持平台自动生成、保存并复用密钥，包括 Windows |
| 指定 `EncryptionKey` | 使用应用提供的稳定 32 字节密钥，不另行保存；`Auto` 会选择 AES |
| 指定 `KeyFilePath` | 组件在指定文件中自动生成和复用密钥；`Auto` 会选择 AES |
| 指定 `Protector` | 借用外部保护器，调用方负责生命周期 |

`EncryptionKey` 与 `KeyFilePath` 互斥；DPAPI 不接受 AES 密钥设置；外部保护器不能与显式内置模式或 AES 来源同时指定。密钥长度、枚举值及配置文件与密钥文件同路径等输入在边界检查，不在失败后尝试另一种算法或密钥。

默认自动密钥与配置文件分开保存。`<app>` 取入口程序集简单名称，`config.KeyFilePath` 返回最终路径：

| 平台 | 自动密钥默认位置与落盘方式 |
| --- | --- |
| Windows | `%LOCALAPPDATA%/Confio/keys/<app>.key`，密钥由当前用户 DPAPI 包裹 |
| macOS | `~/Library/Application Support/Confio/keys/<app>.key`，32 字节随机密钥，新建文件权限 `0600`、新建私有目录 `0700` |
| Linux | `$XDG_DATA_HOME/Confio/keys/<app>.key`，未设置时使用 `~/.local/share/Confio/keys/<app>.key`；同样采用 `0600` / `0700` |

显式配置路径不改变默认密钥位置；需要自定义归属时指定 `KeyFilePath`，不额外设置应用标识。相对密钥路径同样在创建或注册时固定。对调用方已存在的目录不擅自改权限；不可写或不可访问时明确失败。macOS / Linux 依靠账户和文件权限，不宣称与系统钥匙串的访问控制等价。内置实现不调用 Keychain、Secret Service、D-Bus 或后台解锁服务；特殊平台设施使用现有 `IConfigurationProtector` 边界。

构造、普通 DI 注册及无须保护的默认值读取不做密钥 I/O。首次需要加密时读取已有密钥；若不存在，在密钥文件协作锁内再次检查，才用密码学随机源生成 32 字节密钥。复用原有临时文件与原子提交实现，密钥持久化成功后才能提交依赖它的配置密文。并发首次创建的所有实例取得同一份最终密钥，不每次启动重新生成。

解密只查找已有密钥，缺失或损坏时保留配置并报错，不能生成替代密钥。文件实例持有已取得密钥的运行时副本，普通读取不重复访问密钥文件；外部删除密钥不清除已打开实例的内存副本，新实例重新取钥后会失败。不实现自动轮换、云同步或恢复服务。

显式密钥在构造时复制；普通 DI 注册冻结输入，各容器根取得自己的运行时副本，释放一个根不影响其他根。注册输入随服务描述的托管生命周期保留，文件释放清零自己的活动加密副本；调用方输入数组仍由调用方管理。外部保护器始终借用，完成后不得保留借用的明文缓冲区；节点转换完成后组件清零明文字节。

AES-GCM 固定使用 12 字节随机 nonce 和 16 字节认证标签，每次加密重新生成 nonce。二进制载荷为 `CFA1`、nonce、标签和密文，外层采用第 6.1 节的 `enc:v1:`，关联认证数据为固定协议与逻辑字段路径。显式密钥模式不访问 DPAPI；Windows 自动密钥模式只用 DPAPI 保护密钥文件。DPAPI 及加密计算按平台同步原语执行，异步路径使用可等待的文件读写与锁等待，不用 Task.Run 包装。

跨机器、跨应用解密需要相同 AES 密钥及逻辑字段路径，不要求程序集名或配置文件路径一致。Windows DPAPI 和 Windows 自动 AES 的本地密钥文件绑定当前用户环境；可移植部署通过显式密钥或部署方管理的密钥文件表达。不把“自动生成并保存”解释为“自动跨机器共享”。同用户权限下能同时读取配置与密钥的程序仍可解密。

实现依据：[跨平台认证加密](https://learn.microsoft.com/en-us/dotnet/standard/security/cross-platform-cryptography#authenticated-encryption)、[Windows ProtectedData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata)、[XDG 目录约定](https://specifications.freedesktop.org/basedir-spec/latest/)。真实平台证据由第 8.1 节维护。

## 7. 源生成、消费与启动

### 7.1 生成范围

源生成器是首版正式能力，采用 `IIncrementalGenerator`，输出配置节声明、静态模型元数据引用、必要的默认构造调用、受保护成员声明和编译期诊断。默认构造直接调用已知类型的 `new`，由模型初始化决定默认值，不反射创建模型。生成声明调用同一运行库的通用注册入口，类型服务及 Options 接线由该入口统一完成，不在生成器中复制注册流程或模型转换器。文件提交、业务校验时点、加密实现及运行状态由运行库负责。生成器编译和打包约束见[开发规范第 5 节](../开发规范.md#5-依赖生成器与-aot)。

原生 `JsonSerializerContext` 声明作为共同输入：.NET 生成器生成序列化元数据，配置生成器生成注册与保护声明，最后共同编译。普通生成器不能依赖另一个生成器的常规输出作为本轮输入，因此不承诺先生成上下文、再由原生生成器二次处理的链式流程，也不增加两阶段构建或自研完整元数据生成器。

同一上下文的 `JsonSerializable` 特性集中在一个 partial 声明上，避免两个生成器按多处声明重复输出。按业务拆分时使用多个上下文，再由文件入口一次性选择，不为此增加生成器间的串联或应用注册代码。

上下文按业务范围或项目组织，不要求所有模型集中到一个全局清单。只处理显式选择的声明；不扫描运行程序集，也不使用全局静态初始化器自动启用所有配置。缺失元数据、不支持的保护声明、同一可见范围内的冲突尽量在编译期报告；组合后才能确定的跨上下文冲突在构造或注册边界拒绝。

Confio 生成器为手写的 partial 上下文补充明确的配置声明清单，运行时通过正式契约取得该清单，不通过反射枚举业务类型。原生 JSON 生成器和 Confio 生成器都读取用户手写的上下文声明，各自输出后共同编译。

手写声明与生成代码调用同一套正式运行时 API，并保持等价的注册语义。`SettingsDeclaration.Create<T>` 接受上下文、配置节路径、`Func<Type, object?>` 默认对象工厂和保护声明；属性与集合信息直接复用原生 JSON 静态元数据。默认工厂直接创建新模型和可默认构造的嵌套对象，其他类型返回 `null`，模型初始化值不复制到生成代码。普通应用全部由生成器接线，手写等价入口不形成另一套转换行为。

### 7.2 应用声明

以下 `MailSettings` 和 `AppSettingsContext` 是应用类型；`SettingsSection`、`Protected` 已由 Confio 提供，`JsonSerializable` 和 `JsonSerializerContext` 是 .NET 原生类型。示例省略 `using`，对应可执行示例见 [ConfioSample](../samples/ConfioSample/MainWindow.axaml.cs)。

```csharp
[SettingsSection("Mail")]
public sealed class MailSettings : IValidatableSettings
{
    public string Host { get; set; } = "localhost";

    public int Port { get; set; } = 587;

    [Protected]
    public string Password { get; set; } = "";

    public void Validate()
    {
        if (string.IsNullOrWhiteSpace(Host))
            throw new System.ComponentModel.DataAnnotations.ValidationException("The mail host is required.");
        if (Port is < 1 or > 65535)
            throw new System.ComponentModel.DataAnnotations.ValidationException("The mail port must be between 1 and 65535.");
    }
}

[JsonSerializable(typeof(MailSettings))]
public partial class AppSettingsContext : JsonSerializerContext
{
}
```

模型本身不需要 `partial`；原生上下文需要。文件格式由入口选择，模型不增加 YAML 或 TOML 专属生成属性。

不可变模型同样加入该上下文的 `JsonSerializable` 声明，更新时使用 `config.Update<RetrySettings>(retry => retry with { MaxAttempts = retry.MaxAttempts + 1 })` 或对应异步入口；可执行模型见 [RetrySettings](../samples/ConfioSample/RetrySettings.cs)。业务校验可同时用于可变类和 `record`。

直接使用和容器接入使用同一份模型与上下文，生成声明负责逐模型接线。两种消费方式分别见第 7.3、7.4 节。

### 7.3 独立消费

无 DI 应用直接创建文件实例并调用读写方法。下面的同步与异步示例使用同一上下文及默认路径，不要求先初始化或取得类型服务；代码为方法体片段。

同步使用：

```csharp
using (var config = new ConfigurationFile(
    context: AppSettingsContext.Default))
{
    var mail = config.Read<MailSettings>();

    mail.Host = "smtp.example.com";
    mail.Port = 465;

    config.Save(mail);
}
```

异步使用，代码位于异步方法中，`cancellationToken` 由调用方提供：

```csharp
using (var config = new ConfigurationFile(
    context: AppSettingsContext.Default))
{
    var mail = await config.ReadAsync<MailSettings>(cancellationToken);

    mail.Host = "smtp.example.com";
    mail.Port = 465;

    await config.SaveAsync(mail, cancellationToken);
}
```

普通 `using` 不影响块内异步读写，所有操作完成后同步释放文件实例；单次异步操作内部的文件流由组件异步释放。

需要观察后续变化时，在文件的使用范围内调用 `using var subscription = config.OnChange<MailSettings>(mail => ApplyMailSettings(mail));`；`ApplyMailSettings` 是应用自己的业务生效方法。容器中对应调用 `settings.OnChange(...)`。订阅不代替首次读取，回调及退订规则见第 4.1、4.2 节。

省略 `path` 时采用第 3.1 节的应用专属可写目录和 `appsettings.json`；需要其他位置或已实现格式时通过同一个构造参数选择。修改模型副本后显式保存；外部修改需要刷新时调用 `Reload` 或 `ReloadAsync`。

### 7.4 普通容器消费

以下 API 已实现；省略 `using`，方法体位于异步方法中，`cancellationToken` 由应用提供。模型和上下文沿用第 7.2 节，普通容器不要求 Host：

```csharp
var services = new ServiceCollection();

services.AddConfigurationFile(
    context: AppSettingsContext.Default);

services.AddTransient<MailService>();

using (var provider = services.BuildServiceProvider())
{
    var mailService = provider.GetRequiredService<MailService>();
    await mailService.ChangeServerAsync(
        "smtp.example.com", 465, cancellationToken);
}
```

业务服务通过构造函数取得类型服务，在业务方法内读写；构造函数只保存依赖。此处更新两个字段，模型的其他属性从最新文件值取得：

```csharp
public sealed class MailService
{
    private readonly ISettings<MailSettings> _settings;

    public MailService(ISettings<MailSettings> settings)
    {
        _settings = settings;
    }

    public Task ChangeServerAsync(
        string host, int port, CancellationToken cancellationToken)
    {
        return _settings.UpdateAsync(
            mail =>
            {
                mail.Host = host;
                mail.Port = port;
            },
            cancellationToken);
    }
}
```

业务服务也可调用 `_settings.Read()`、`ReadAsync`、`Save`、`SaveAsync` 及其他成对操作，不需要逐模型工厂或额外适配类。示例中的 `BuildServiceProvider()` 是应用构建最终容器，所有异步操作结束后由其释放文件；注入的 `ISettings<T>` 无需业务代码释放。需要整文件重载时，注入同一个 `ConfigurationFile` 调用 `Reload` 或 `ReloadAsync`。

### 7.5 原生读取接入与启动

接入原生读取时，Confio 只完成自己的预加载和注册，随后由应用调用原生 `Build`。单个上下文、多个上下文和已有文件都有同步及异步重载：

| 入口 | 同步 | 异步 |
| --- | --- | --- |
| 普通容器与配置根 | `services.AddConfigurationFile(configuration, context, ...)` | `await services.AddConfigurationFileAsync(configuration, context, ...)` |
| `IHostApplicationBuilder` | `builder.AddConfigurationFile(context, ...)` | `await builder.AddConfigurationFileAsync(context, ...)` |

只使用文件或 `ISettings<T>` 时按第 7.4 节普通注册即可。需要 Configuration / Options 时，原生读取入口在返回前建立可读快照；消费者构造、同步索引器及 Options 工厂不等待异步初始化。

```csharp
var services = new ServiceCollection();
using var configuration = new ConfigurationManager();
await services.AddConfigurationFileAsync(configuration, AppSettingsContext.Default,
    cancellationToken: cancellationToken);

services.AddTransient<MailService>();
using var provider = services.BuildServiceProvider();
var mail = provider.GetRequiredService<IOptionsMonitor<MailSettings>>().CurrentValue;
```

配置源按原生顺序追加。应用可以在接入前后添加其他来源，组合根保留原生优先级；默认 Options 的数据来源仍遵守第 4.4 节。已有 `IConfiguration` 显式服务注册不会被覆盖，其他配置根的组合和生命周期由应用按原生机制处理。

只需选定文件的 Host 使用空构建器，日志和业务服务在配置已可读后正常注册。`MailWorker` 的可执行示例见[容器场景](../samples/ConfioSample/IntegrationExamples.cs)：

```csharp
var builder = Host.CreateEmptyApplicationBuilder(null);
await builder.AddConfigurationFileAsync(AppSettingsContext.Default,
    cancellationToken: cancellationToken);
builder.Logging.AddConfiguration(builder.Configuration.GetSection("Logging")).AddConsole();
builder.Services.AddHostedService<MailWorker>();
using var host = builder.Build();
await host.RunAsync(cancellationToken);
```

向已有 Host 接入时保留它的配置来源、容器工厂、日志规则及原生 Build；不建立另一个 HostBuilder 或捕获 IConfiguration 工厂。Host 的环境、内容根等先于文件加载确定，后加载的文件不倒改这些启动选择。使用 Host 的应用引用完整 Hosting 包；运行库只依赖实际需要的抽象。

预加载依次检查选项与归属、加载或复用成功快照、建立原生投影、添加配置源与类型服务及 Options 接线。新文件在交接前失败或取消时由组件释放；已有文件始终借用。接入后自建文件归配置源管理，随 ConfigurationManager 或 Host 释放，即使从未解析业务服务也一样。普通配置根由调用方的 `using` 管理，DI 中该文件作为已有实例借用，不再增加另一套所有权。

组件不接管整个容器或 Host 的构建失败，不清理应用的其他 Provider 或服务，也不要求替换原生 Build。原生集成错误和业务启动失败在应用的启动边界处理，配置根仍按其原生生命周期释放。文件本身的保存、快照及通知规则保持不变。

预加载成功只说明文件持久化规则通过。Options 创建、缓存、原生校验和 ValidateOnStart 继续按第 4.4 节执行，不提前承诺业务服务启动成功。最终日志可在预加载之后读取配置；Confio 不创建日志 Provider、全局 Ready 状态或第二个容器。

### 8.2 实施次序

当前阶段以直接使用 `ConfigurationFile` 的完整配置行为为重点，四种格式已经接入同一运行库。按实际场景核对数据语义和失败边界，发现缺口就修复所属实现；接口已经存在或示例能够运行，不表示其他平台已经验收。.NET 10、真实源生成与 Native AOT 继续作为核心实现基线。

1. 完善直接读写流程：首次加载、模型默认值、编辑副本、显式保存、基于最新值更新、重置及外部修改后重载。同步与异步遵守同一语义，应用不额外初始化或复制通用默认行为。
2. 核对模型与数据语义：多模型共享文件、嵌套对象、集合、字典、不可变模型、缺失值与显式空值、业务校验、非目标配置节保留，以及中文和多行文本的读写体验，均符合第 3、4、5 节约定。
3. 完善文件可靠性：原子提交、跨实例和跨进程更新、取消、损坏输入、权限和替换失败、快照与通知的一致性。实际使用环境中已经发现的文件提交问题优先定位，应用不自行管理文件锁、临时文件或提交失败清理。
4. 核对配置保护：字符串与整个子对象真实加解密，密钥缺失、错误用途、篡改和保护失败时保留文件与成功快照；同步与异步共用保护语义，验证实际非空值。现有目标上的核心保护验收随相关变更执行。
5. 用测试、真实消费者和 Sample 验证上述配置行为，示例只补当前核心场景需要的观察与操作。公共契约、文件提交、保护、生成器或包交付有变化时，按第 2.1 节完成受影响运行时与现代 JIT / Native AOT 验收；共享改动影响已有 DI / Configuration / Options / Host 时执行必要回归。

现有多目标支持复用配置核心与同一包，按真实消费者维护数据语义及平台证据。后续按明确需求深化 DI / Configuration / Options / Host、评估额外格式，并补充未验收的平台；第 2.1 节之外的运行时不预建资产或分支。应用不增加逐模型、逐格式或逐运行时的基础设施接线。

本阶段的完成依据是第 8.3 节中配置核心的行为验收、可运行的直接消费场景，以及与实际实现一致的使用说明。已有证据充分且没有新问题的能力不重复实施或验收；备份恢复不列为待补功能。既有集成随受影响的共享变更回归；集成深化、额外格式和未纳入本阶段的平台适配按各自阶段验收，不作为当前配置功能完善的前置任务。

### 8.3 验收边界

| 验收面 | 必须观察到的结果 |
| --- | --- |
| 直接消费与加载 | 构造不访问配置文件或密钥、不创建目录；首次同步或异步读写自动加载，失败和取消不发布半成品；首次保存、更新和重置无需应用先读取 |
| 同步与异步 | 五组读写操作在支持目标上遵守相同数据语义；混用两种入口仍共享同一文件状态，I/O 与等待采用对应路径，不以阻塞任务或线程池包装冒充另一种能力 |
| 快照与显式保存 | 文件和 `ISettings<T>` 的每次读取获得独立副本，修改不自动保存；加载后普通读取不访问文件或密钥；外部修改经显式重载或成功协调提交生效 |
| 默认值与数据语义 | 无文件读取不落盘；可变类和 `record/init` 的缺失值、显式 `null`、嵌套替换、空容器、集合替换和重置符合声明；无范围校验且默认 `587` 的属性保存 `0` 后仍读到 `0` |
| 业务校验 | 直接创建和 DI 自动执行同一模型规则；首次加载、重载、保存、两种更新和重置在发布前校验，失败保留文件、快照与令牌；普通读取不重复执行；Options 原生校验保留自己的时序 |
| 直接订阅 | 文件和类型服务无需 Options 即可订阅；订阅不触发加载或初次回调，成功提交或重载才通知，各回调取得独立副本，可退订；回调在锁外可重入，单个订阅失败不影响其他订阅或撤回已提交结果 |
| 单文件与归属 | 多模型共用选定文件；同节及父子归属冲突被拒绝；保存保留非目标配置节 |
| 并发 | 同步与异步首次读取不重复初始化或覆盖后续提交；同进程与同包多进程的不同配置节更新不互相覆盖；`Update` 基于协调范围内的新值执行一次；同实例重载不会在后续保存成功后发布先前读到的旧快照 |
| 提交与取消 | 写入或替换失败不发布候选快照；提交后取消和通知失败不伪装成未保存 |
| 格式 | 同一模型在各格式支持范围内往返；INI 区分数值属性与保留前导零的字符串，拒绝索引缺口与不可表达值；修改其他节不改变 TOML 原生日期与字符串的类型，数值精度和区域规则不漂移 |
| 保护 | 缺失、`null` 和空字符串不获取密钥或补写；非空值及非 `null` 子对象按规则保护；首次加载及重载自动保护现有明文，明密文混合时保留已有密文；文件保留前缀错误不降级，模型前缀输入能完整往返且只解密一层；命名策略不遗漏声明，组件输出的文件、临时文件和诊断不泄漏受保护明文 |
| 普通 DI | 一次注册覆盖所选模型，注册、构建与解析 Confio 服务不做文件或密钥 I/O；根容器和不同作用域中的默认类型服务共用各自所属文件实例，作用域释放不释放文件；重复注册及配置节冲突明确失败，显式替换保留；首次同步或异步业务操作自动加载 |
| 原生数据来源 | Confio Provider 投影与类型服务共用文件实例，默认 Options 工厂从其当前快照创建初始值；已有组合根保留其他 Provider 的优先级，覆盖值不串入文件读写；普通 DI 不意外添加原生读取投影 |
| Options | 默认命名工厂保留原生配置和校验流程；保存后 `IOptions<T>` 与已取值的作用域快照保持缓存，Monitor 刷新、新作用域首次取值取得新快照；修改 Options 对象不改变文件快照，校验失败不回滚已提交文件；应用无需逐模型绑定、工厂注册或 AOT 豁免 |
| 生成器 | 真实输出编译、冲突序列化选项及保护声明的诊断、多上下文、多项目消费及手写等价性成立；不依赖普通生成器输出串联 |
| 启动与释放 | 原生读取投影先于最终日志及业务服务可用；普通 DI 的自建实例由根释放，外部实例始终由调用方释放；原生 Add 入口在加载失败或取消时清理尚未交接的自建文件，成功后由配置源及其配置根负责释放，应用继续使用原生 Build 与生命周期。每次操作清理自身资源，退出前完成操作，`Dispose` 不隐式保存或等待异步操作 |
| 目标与包消费 | 按第 2.1 节验证八个运行库资产和依赖组、九种消费目标的自动选择、模型类库的跨项目消费及真实应用运行；同一候选包中生成器正常加载，不成为应用运行依赖；跨运行时使用同一 AES 密文协议 |
| Native AOT | 现代消费者按交付 OS / 架构实际发布并运行四种格式、默认值、读写、加解密及原生集成路径；不能仅发布未调用组件的空程序，生成器与 Roslyn 不进入运行产物 |
